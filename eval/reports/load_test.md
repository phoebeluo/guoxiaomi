# 服务层压测（W12）

- 时间：2026-11-02 12:13:08
- 被测：Flask `/chat`（检索 + 拼 prompt + 落盘），**模型为 mock**，固定 50 ms
- 入口限流：`MAX_INFLIGHT=8`，超出返回 503
- 每档 40 请求，单进程单 worker（threaded）

## 结果

| 并发 | QPS | 较上档增长 | P50 | P95 | P99 | 200 | 503 | 500 |
|---|---|---|---|---|---|---|---|---|
| 1 | 16.0 | —% | 57 ms | 81 ms | 82 ms | 40 | 0 | 0 |
| 4 | 62.0 | 288% | 59 ms | 79 ms | 81 ms | 40 | 0 | 0 |
| 8 | 109.8 | 77% | 60 ms | 77 ms | 79 ms | 40 | 0 | 0 |
| 16 | 83.3 | -24% | 76 ms | 79 ms | 80 ms | 12 | 28 | 0 |
| 32 | 97.1 | 17% | 74 ms | 90 ms | 91 ms | 13 | 27 | 0 |

## 瓶颈定位

**拐点在并发 16**：QPS 较上一档增长不足 20%，加并发不再换吞吐，只换排队。
并发 1 时 QPS = 16.0，峰值 QPS = 109.8。

这不是应用层算力不够，而是**入口信号量先满了**：超过 `MAX_INFLIGHT=8` 的请求直接被 503 拒绝。
换句话说，**吞吐上限是我自己设的，不是硬件逼出来的** —— 这个数该由上游 RPM 决定，不该由 worker 数决定。

## 为什么瓶颈不在应用层（这才是结论）

| 层 | 单次开销 | 是否瓶颈 |
|---|---|---|
| 检索（45 篇向量，numpy 余弦） | 约 4 ms | 否 |
| 拼 prompt + 落盘 | 约 3–8 ms | 否 |
| **模型生成** | **数百 ms ~ 数秒** | **是** |

真实流量下，QPS 上限 = 上游 RPM ÷ 每请求 token 量，与我的 worker 数无关。
所以并发保护做在**入口**（信号量 + 503 + Retry-After），而不是拼命加 worker——
加 worker 只会让更多请求同时卡在上游等待，把 429 变成超时。
