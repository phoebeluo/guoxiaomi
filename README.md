# 果小蜜 · 水果电商客服智能体

一个面向电商客服场景的 LLM 应用，重点不在"能聊"，而在**每个结论都有可复现的数字**：
60 题评测集、可审计的金标、以及一套把评测判据本身也当被测对象的纪律。

> 定位：独立的个人项目。语料、题库、判据、结论全部自建；不依赖 LangChain 等框架。

---

## 三个数字

| 结论 | 数字 | 怎么来的 |
|---|---|---|
| 检索质量不随语料规模衰减 | 45 → 346 篇（7.7 倍），块级 **R@5 恒定 95.8%**，MRR 0.851 → 0.880 | 同一批 52 题、同一套指标，四档语料各跑一遍 |
| 检索端只损失 2 pp | 理想检索 **100%** / 真实 BM25 检索 **98%**，失效定位到 #6 单题 | C/D 对照组，逐题复核 |
| 评测集本身可信 | 金标「独立支撑」审计 **54/54** 通过，0 冗余、0 库外污染 | 用一个脚本去判金标原文，不靠人工声称 |

配套的诚实标注：**瓶颈不是语料规模，而是口语 ↔ 书面语的词汇鸿沟**
（未召回组 token 覆盖率 13%，已召回组 45%）。

金标审计、覆盖度、数字口径一致性、错误分类、历史截断、删会话行为等。

## 已知边界（不掩饰）

- 线上检索已接入（`RETRIEVAL=on` 为默认，BM25 top-3 **篇**注入；`off` 保留全量注入作 A/B 对照）：system 由 33,211 字符降至均值 **5,780**（P95 6,298 / max 6,438，压缩 5.75 倍）
- **线上索引只含冻结的 45 篇**。301 篇外部语料仅用于评测侧规模实验 —— 实测其异构噪声在块级 R@5 上不衰减，但在口语提问下会误命中（「这单能赔多少」命中《能力验证不合格怎么办》），且单篇长文可把 system 撑到 18.7K 字符。需要复现 346 档线上路径时设 `RETRIEVAL_EXTRA=data/raw/external_clean`
- 无 pytest / CI、无 FastAPI / Docker、无 function calling（W8 / W9 / W12 计划中）
- 留出集 8 题的复述与金标抽检属本人所有权事项，尚未补完，故暂不引用留出集数字
- 判据有两个已知缺陷：J1「查不到」误伤、J2 远距离否定剔除失效（已登记，未修）
- 外部语料 301 篇只做运行时拼接，不参与冻结，因此 346 篇档指标不复现 45 篇档的历史基线

## 设计取舍（为什么有些常见方案没上）

| 没上 | 理由 |
|---|---|
| 向量库（Chroma / FAISS） | 2,562 块规模下 numpy 余弦 3 ms，装库是负债不是能力 |
| LangChain / LangGraph | 链路只有"检索 → 注入 → 生成"三段，框架带来的抽象成本高于收益 |
| Rerank | 算过成本与收益，当前规模不值；这个判断本身比硬上一个 rerank 更值得说 |
| 类别路由 | BM25 已是检索器，再叠一层关键词路由是两件事做同一件 |

### BM25 参数：为什么是 `k1=1.5` / `b=0.75`

1. 取论文默认值。只扫 `b` 不扫 `k1`：`k1` 控词频饱和，而本题库查询的词频几乎恒为 1–2，扫它无区分度；`b` 控长度归一化，346 篇档文档长度相差 20 倍以上，「长文霸榜」完全由它决定。
2. `b ∈ {0.5, 0.75, 1.0}` × 346 篇 × 48 题实测（零 API，`tools/sweep_b.py`）：块级 R@5 **三组恒定 95.8%**，MRR 0.892 / 0.880 / 0.880。`b=0.5` 的 +0.012 只相当于 **1 道题**（48 题里 1 题 = 2.1 pp），是噪声。
3. **故沿用默认 0.75，不采纳表面最优值**——按「数字最好看就选它」等于把参数过拟合到 48 道题上。结论：长度归一化不是瓶颈，与 W4「规模不是瓶颈」互为支撑。见 `eval/reports/b_sweep.md`。
