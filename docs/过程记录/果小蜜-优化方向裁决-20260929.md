## 四、推荐路径：P0 全量注入

### 4.1 为什么它是最简单的

注入全部语料后 token 开销约 **21,197**（按中文 1 字 ≈ 1 token 的保守口径估算，含 Markdown 符号）。`deepseek-v4-pro` 上下文窗口远超此量，**一次请求就能塞完**。

这意味着：不需要切分、不需要 embedding、不需要向量库、不需要重排。一个 `glob` + 一个字符串拼接就完事。

### 4.2 落点

在 `app.py` 第 7 行 `load_dotenv()` 之后加一个"启动时一次性读取全部 md、拼成一个大字符串"的动作；在第 216 行拼 messages 时，把它接在系统提示词后面。

三个必须守住的约束：

1. **只读一次，缓存起来。** 不要每轮对话都读 44 个文件。
2. **务必放在 messages 列表的最前面。** DeepSeek / DashScope 的 prefix cache 对"固定不变的前缀"有命中优化。语料在系统位且内容稳定，多轮对话时能反复复用这部分，边际成本显著下降（具体折扣以控制台账单实测为准，别信我给的比例）。
3. **每篇前面加来源标注**，形如 `【来源：百科-柚子】`。这样后面接 BM25 时可以复用同一套拼接代码，也方便你肉眼核查答案到底来自哪篇——做归因分析时能救命。

### 4.3 代价，说清楚

| 维度 | 影响 | 量级 |
|---|---|---|
| 单次请求输入 token | +~21k，固定成本 | 每轮都付，与对话轮数无关 |
| 首字延迟 | prefill 变长 | 多轮后基本感知不到（命中 cache 时） |
| 上下文占用 | 21k 固定 + 历史线性增长 | **这才是真风险**，见 4.4 |
| 效果 | 拒答率断崖下降 | 具体数字要你实测得出，不要抄别人的 |

单价请你自己去百炼控制台查 `deepseek-v4-pro-0813` 的输入单价，用「21,197 ÷ 1,000,000 × 单价」算出每次的准确成本。**这个数字写进简历前必须自己算过一遍。**

### 4.4 一个必须同步处理的问题

`app.py:213-218` 每轮都把**完整历史**发给模型：

```python
{"role": "system", ...},
*st.session_state.messages      # ← 全量历史，无截断
```

历史是线性增长的。注入 21k 语料后，可用上下文变成 `21k + 历史`，留给对话的空间被压缩了一半以上。长对话会先变慢、再变贵、最后直接报上下文超限。

不要求你现在就做摘要压缩，但至少要先做 **`history[-N:]` 保留最近 N 轮**（比如最近 10 条 = 5 轮），5 分钟内能改完。更优雅的做法是"超 N 轮后调用一次模型把更早的内容压缩成摘要"，留到后面做。

### 4.5 一个现在不炸、将来必炸的坑

第 216 行用的是 `system_prompt.format(name=..., character=...)`。`str.format` 会把 `{` `}` 当占位符解析。好消息是当前 44 篇语料里**花括号数量为 0**，所以接进去不会立刻崩。

坏消息是：这是一个定时炸弹。你只要往库里加一篇含 `{` 的文档（JSON 示例、模板占位符、数学公式都会带），`.format()` 立刻抛 `KeyError` / `ValueError`，而且报错信息离真正的病因很远，很难查。

所以**注入时请绕开 `.format()`**，改用不会被花括号误伤的替换方式，或者在注入前把语料里的 `{` `}` 转义。这件事现在做成本是 0，以后做成本是半小时的 debug。

## 五、再往后一步：文件名路由（这才是真·检索的雏形）

全量注入跑通之后，第二步不要直接跳 BM25，先做 **20 行版本的路由**：

你的文件名是 `类别-主题.md`，类别只有 9 个。那么：

1. 用户提问里识别出类别词（"退钱"→ 售后 / "运费"→ 配送 / "柚子"→ 百科 / "积分"→ 会员）
2. 只注入该类别下的文档，token 从 21k 降到 2k–11k
3. 命中不了类别时退回全量注入

这一步的价值不在于省 token，而在于它逼你思考三件事：**召回不到怎么办、路由错了怎么办、怎么衡量"注对了"**。这三个问题正是 BM25 真正的难点，提前用最小成本踩一遍。

完整演进路线：

| 阶段 | 做法 | Token/次 | 你要能讲清的东西 |
|---|---|---|---|
| P0 基线 | 全量注入 | ~21k | 为什么要有 baseline |
| P1 路由 | 文件名/关键词命中类别 | 2–11k | 召回失败的兜底策略 |
| P3 | chunk + BM25 | 1–3k | 为什么 BM25 优于关键词、切分粒度如何调 |
| P4（可选） | embedding 稠密检索 | 1–3k | 稀疏 vs 稠密的取舍、什么时候不必上向量库 |

你在 `rag/chunk.py` 做的切分属于 P3。**注意：这条路线上，你可以合法地把 P0 和 P1 的结果作为"对照组"写进评测报告**——面试官问"你怎么证明 BM25 比暴力注入好"，你要是答不上来，那个 BM25 就是黑盒调参。反过来，有对照数据的 RAG 和无对照数据的 RAG，完全是两个含金量。

## 七、怎么证明有效（不要跳过）

改完之后，别急着往下走。做一次最小验证：

1. 挑 8–10 个问题，覆盖不同类别（至少包含：柚子/芒果这类百科、运费/包邮门槛、坏果赔付、会员日折扣、发票）
2. 用同一批问题，**改前跑一遍、改后跑一遍**，把回答存下来
3. 人工标三个维度：**是否拒答 / 事实是否正确 / 是否引用了真实语料内容**
4. 得到「拒答率 X% → Y%」这样的数字

这批问题就是你的评测集雏形，后面做 BM25 时复用同一套，四列横向对比。**这组对比数据是整个项目最值钱的东西**，比 BM25 本身值钱。

## 附录 B：关于 rag/chunk.py

按分工约定，实现由你自己完成，我只指出**会在运行时报错的结构性问题所在位置**，不给改法：

- 第 19–27 行区域：`buf` 的初始类型与你后续对它调用的方法不匹配，一处是按 **`""`（字符串）** 初始化，另一处却对它调用列表方法 `.append()`；同时第 26–27 行的缩进，使得每个句子都会往 `chunks` 里追加一次，而不是每凑满一块才追加一次。

- `get_tail()` 第 40 行 `tail = s + tail`：`tail` 若已被 `buf = tail` 赋值为字符串或列表，这里的加号语义需要与它保持一致。
