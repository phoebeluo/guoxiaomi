## 第 1 部分 · 四个核心概念（必背）

### 1.1 虚拟环境是「产物」，不是「源码」

`.venv` 是我的机器上装出来的**结果**，不是项目的一部分。它有三个特征决定了它不能进 Git：

- **体积**：293 MB，而我的整个源码才几十 KB
- **平台绑定**：`Scripts/python.exe` 是 Windows 二进制，拿到 Linux 上完全没用
- **不可读**：上千个文件全是编译好的库，code review 时没人能评审它

所以 `.gitignore` 里必须有 `.venv/`。别人拿到我的仓库，靠 `requirements.txt` **重建**一个属于他自己的环境。

> 一句话说法：虚拟环境是构建产物，跟 `node_modules`、`dist/` 一样，只提交"怎么造"的说明书，不提交造好的东西。

### 1.2 声明式依赖：把「环境长什么样」写进文本

| 方式 | 别人要做什么 | 问题 |
|---|---|---|
| 把 `.venv` 打包发给别人 | 解压就能跑 | 体积巨大、平台绑定、无法 review、无法增量更新 |
| 给一个 `requirements.txt` | `pip install -r requirements.txt` | 无 |

**声明式**的意思是：我不描述"执行了哪些安装命令"，而是声明"最终需要哪些包、什么版本"，由工具去把它实现出来。

### 1.3 直接依赖 vs 传递依赖（3 对 48）—— **这条最容易被面试官追着问**

我的代码里只 `import` 了三个第三方包：

```python
import streamlit as st          # UI 框架
from openai import OpenAI       # 调用大模型
from dotenv import load_dotenv  # 读 .env 里的 API Key
```

但这三个包自己还要依赖别人：`streamlit` 要用 `pandas` 处理表格、`pyarrow` 处理列式数据、`altair` 画图；`openai` 要用 `httpx2` 发请求、`pydantic` 做数据校验。**一层层展开后就是 48 个**。

- **直接依赖（direct）** = 我代码里显式 import 的 → 3 个
- **传递依赖（transitive / 间接）** = 被直接依赖拉进来的 → 45 个

**为什么要连传递依赖一起锁？** 因为 `streamlit` 自己不锁死它依赖的 `pandas` 版本。如果只写三个直接依赖，别人装的时候可能拉到新版的 `pandas`，行为变了、我的代码就崩了——而报错地点在 `streamlit` 里面，极难排查。

> 如果面试官问"那你只写三个行不行"——答：**能解释得清就行，但不锁传递依赖就失去了可复现性**。工程上牺牲一点可读性换取确定性，是划算的。

### 1.4 可复现构建（reproducible build）—— **必须能讲，这是本步的立意**

**不锁版本会发生什么**：今天能跑，三个月后别人 clone 下来装不上或跑出错。原因可能是某个依赖发了新的大版本、改了函数签名。这类 bug 的可怕之处是**你的代码一个字都没改**。

加了 `==` 之后，任何时候、任何机器上装出来的环境都一模一样。

**我做过的一次真实验证**（可以直接当案例讲）：

```
1. uv venv --python 3.14 建一个全新空环境
2. uv pip install -r requirements.txt
3. 用这个新环境无头运行 app.py
→ 启动成功，无异常
```

这就证明了这个文件**真的能复现环境**，而不只是"看起来写了"。

## 第 2 部分 · 面试问答预演

### Q1：你们项目怎么保证别人拿到代码能跑起来？

答：项目里有 `requirements.txt`，48 个包全部锁定到具体版本。别人用 `uv pip install -r requirements.txt` 就能装出和我一致的环境。API Key 走 `.env` 文件，不提交到仓库，仓库里只放一个 `.env.example` 说明需要哪些变量。

> ⚠️ 注意：`.env.example` **你还没做**，别说了。现在只说前半段。

### Q2：为什么 requirements.txt 里有 48 个包，你代码里只 import 了 3 个？

答：那 3 个是直接依赖，另外 45 个是它们拉来的传递依赖。我选择连传递依赖一起锁定，是因为直接依赖本身不会锁死它们自己的依赖版本——只写 3 个的话，别人装的时候可能拿到不同版本的 pandas，导致行为不一致。**这是我主动选择牺牲一点可读性换确定性。**

### Q3：为什么 `.venv` 不进 Git？

答：三个原因：体积 293 MB；里面是 Windows 平台的二进制，换到 Linux 完全不可用；而且全是编译产物，无法 code review。虚拟环境是可重建的构建产物，只需要提交重建的方法。所以 `.gitignore` 里加了 `.venv/`。

### Q4：`pip freeze` 有什么缺点？有更好的方案吗？

（这条是**加分题**，答出来能拉开差距）

`pip freeze` 的问题：
1. **不区分直接依赖和传递依赖**——48 行全平铺，新同事看不出哪几个是业务代码真正用的
2. **不带哈希校验**——只锁版本号，无法防住"同版本号被重新上传了不同内容"（供应链攻击面）
3. **只锁 Python 包，不锁 Python 解释器版本和系统库**——换了 Python 版本仍可能出问题

更好的方案：
- **`pyproject.toml` + lock 文件**：`pyproject.toml` 声明"我直接需要什么"（人读），`uv.lock` / `poetry.lock` 记录完整依赖图**并带哈希**（机器用）。职责分离。
- **Docker**：把解释器、系统库、依赖全部固化进镜像，是终极的可复现方案。

我目前用的是最轻量的方案（requirements.txt），因为这个项目小、协作方是我一个人；如果要做团队协作或部署上线，我会换成 `pyproject.toml` + `uv.lock`。

### Q5：你是怎么做环境排查的？—— **这条最值钱，是真实故事**

完整过程（**照着讲就是标准的 ST-A 结构**）：

1. **现象**：项目里有个 `.venv`，以为运行用的就是它。
2. **验证**：直接把 `app.py` 的 import 列表拉出来（`streamlit` / `openai` / `dotenv`），拿 `.venv` 的解释器逐个 `import` 试 → `streamlit` 成功，**`openai` 和 `dotenv` 都 `ModuleNotFoundError`**。
3. **交叉验证**：列出 `.venv/Lib/site-packages` 的 82 个目录，逐个对照 → **全部是 streamlit 及其传递依赖**（pandas、pyarrow、numpy、altair、pydeck…），一个 LLM SDK 都没有。结论：这是"只装了 streamlit 的 venv"。
4. **排除干扰**：再去试另外两个候选解释器——uv 的基础解释器和系统 Python。发现 uv 基础解释器是**裸的、零包**（它只是 venv 的 base，不该直接当运行环境）；系统 Python 3.13 反而依赖齐备。
5. **修复**：`uv pip install --python .venv/Scripts/python.exe openai python-dotenv`，补上缺的包。
6. **验证**：用 Streamlit 官方 `AppTest` 接口无头跑真实 app，发一问「琯溪蜜柚什么时候上市？」→ 答出语料里的"10 至 11 月、福建平和" → **证明改动后链路真的通，不是"应该能跑"**。

**这段能体现的能力**：从 import 反推依赖、用目录列表做交叉验证、区分"基础解释器 vs 虚拟环境"、用可重复的自动化方式验证修复结果。

> 面试官很爱问"你遇到过什么坑、怎么解决的"。**这一段比"我做了个 RAG 项目"更能证明你会干活**，因为它有排查路径、有证据、有闭环。建议在简历项目描述里留一行给"环境可复现性"，面试时展开讲这个故事。

## 第 3 部分 · 知道就好的细节（听懂即可，别硬背）

| 细节 | 说明 |
|---|---|
| **uv 的硬链接机制** | uv 有全局包缓存，装包时默认用硬链接复用，省磁盘、装得快。我这次看到告警 "Failed to hardlink files; falling back to full copy"——原因是**缓存目录和项目目录不在同一个磁盘分区**，硬链接跨分区不可用，只能退化成复制。这是 uv 的 `UV_LINK_MODE` 控制的。 |
| **uv 建的 venv 没有 pip** | `uv venv` 默认不装 pip（更快更干净）。所以在这个环境里不能直接 `pip install`，要么用 `uv pip install`，要么 `python -m ensurepip` 补上。这对新手是个容易卡住的点。 |
| **为什么选 uv 而不是 pip / conda** | uv 是 Rust 写的，装包速度比 pip 快一个量级；同时管 Python 解释器版本和虚拟环境，不用另外装 pyenv + virtualenv；lock 能力也比 requirements.txt 强。conda 更偏数据科学的重型环境，这个项目用不上。 |
| **Python 3.14 偏新** | 我的 venv 是 3.14.7。**新版本 Python 上部分第三方库可能还没适配**。如果哪天遇到莫名其妙的报错，换 3.12 试试是合理的排查动作。这个认知本身可以讲。 |
| **版本约束符** | `==1.2.3` 精确锁定；`>=1.2` 只保底；`~=1.2.3` 允许补丁位浮动（等价 `>=1.2.3,<1.3`）；`^` 是 Poetry 语法（允许不改变最左非零位）。**生产部署偏好 `==`，库开发偏好 `>=`**。 |
| **依赖安全扫描** | `pip-audit` / `uv pip audit` 可以查已知 CVE。项目上线前值得跑一次。 |

# 附篇 · Git 版本控制：面试可讲清单

> 与依赖管理的共同点：**两者都是"让别人能接住你的工作"的工程规范**。面试官问"你怎么管理代码"，考的就是这个。

## A. 三个区（必背）

```
工作区（Working Directory）  ← 你正在编辑的文件
    ↓ git add
暂存区（Staging Area / Index） ← 准备提交的那批改动
    ↓ git commit
本地仓库（Repository / .git） ← 永久存档的提交历史
```

**暂存区存在的意义**：让你**只提交完成的工作**。你手上可能同时有"已经跑通的功能"和"改一半的实验代码"，`git add` 挑出前者提交，后者留在工作区继续改。这不是多余的步骤，它是**提交粒度的控制手段**。

## B. 提交粒度：一个提交只做一件事（必背）

**反面例子**（新手最常见的做法）：

```
git add .
git commit -m "更新"
```

问题：一次提交里混了新增功能、修 bug、改格式三件事。哪天要只回退其中一件，做不到——只能整块回退。

**正确做法**：一个提交 = 一个逻辑改动 + 一条说清它做了什么的信息。

**为什么面试官在意这个**：他真正想看的是"这个人有没有想过别人接手"。粒度清晰的提交历史，等于一份自动生成的开发日志——面试前你可以翻自己的 `git log` 回忆"我当时是怎么一步步做的"。

## C. 提交信息规范：Conventional Commits（必背）

格式：`<类型>: <做了什么>`

| 前缀 | 用于 |
|---|---|
| `feat` | 新增功能 |
| `fix` | 修复 bug |
| `chore` | 杂务（依赖、配置、构建） |
| `docs` | 文档 |
| `refactor` | 重构（行为不变） |
| `test` | 测试代码 |

例：

```
feat: 新增语料加载器，44 篇语料拼为单一上下文
fix: 修复删除会话会清空当前会话内容
chore: 锁定项目依赖（48 包）
```

> 你已有的那次提交 `chore: 初始化仓库，纳入语料与脚本基线` 用的就是这个规范，保持下去。

## D. 安全边界：什么绝不能提交（必背）

| 文件 | 为什么不能提交 |
|---|---|
| `.env` | **里面是 API Key。一旦推到公开仓库，会被爬虫在几分钟内扫到并盗刷**。你的项目里 Key 目前未被追踪，这是对的。 |
| `.venv/` | 293 MB 的二进制产物，平台绑定，不可 review |
| `__pycache__/` | Python 自动生成的编译缓存 |
| `data/sessions/` | 个人对话数据，非源码 |

这四个都已在 `.gitignore` 里。**面试可以主动讲这一条**——它同时体现"安全意识"和"知道什么属于构建产物"。

## E. 面试问答预演

### Q1：你平时怎么管理代码？

答：用 Git 做版本控制，按"一个提交只做一件事"的原则拆提交，提交信息用 Conventional Commits 规范（feat / fix / chore 前缀）。`.env`、`.venv`、`__pycache__` 这类不该进仓库的东西都在 `.gitignore` 里。

### Q2：如果改到一半改坏了想退回怎么办？

答：因为我在每个可运行的节点都做了提交，所以可以直接回到上一个提交的状态。**这也是我为什么先在依赖和环境上做规范化、再动业务代码——先给自己留退路。**

（如果你还没用过 `git checkout` / `git restore` 回退，**这条先别说**，等实际操作过一次再讲。）

### Q3：为什么 `.env` 不能进仓库？

答：里面是我的大模型 API Key。Git 的历史是永久的——就算后来删掉再提交一次，Key 仍然留在历史记录里，任何能 clone 的人都能翻出来。正确做法是提交一个 `.env.example`，只写键名、不写值。

### Q4：你会用分支吗？/ 你用过 PR 流程吗？

**如实答**：目前是个人项目，只用到主干提交（`add` / `commit` / `log` / `status` / `diff`），**还没有多分支协作的经验**。下一步想在实际项目里练分支和合并。

> ⚠️ **红线**：**不要**说自己"熟练使用 Git"、"会用 rebase / stash / cherry-pick"。面试官只要追问一句就会露。**如实说会哪几个命令，比含糊地说"会用 Git"安全得多，而且更显真诚。**

## F. 简历怎么写

不要把"会用 Git"当独立条目写（那是所有候选人的默认项，写了不加分）。

把它融进项目描述的**执行层面**，或者干脆不写——**面试时讲得出"我按 feat/fix 拆提交、把 .env 挡在仓库外"这件事，比在技能栏写"Git"有用得多**。
