# Step 0 · 清场

## 0-A　`app.py:66-68` 删除任意会话都会清空当前会话

### 现象

```python
def delete_session(session_name):
    try:
        session_path = os.path.join(SESSIONS_DIR, f"{session_name}.json")
        if os.path.exists(session_path):
            os.remove(session_path)
            # 如果删除的是当前会话          ← 注释是这么写的
            st.session_state.messages=[]                        # 但没有判断！
            st.session_state.current_session=generate_session_name()  # 无条件执行
            st.rerun()
```

注释承诺"如果删除的是当前会话"，代码却无条件执行。后果：**你加载了会话 A，在历史列表里删掉会话 B，A 的全部对话当场蒸发且没有落盘。**

### 为什么这是个真 bug 而不是洁癖

Streamlit 的 `session_state` 是内存态，唯一持久化入口是 `save_messages()`。清空 `messages` 之后没有调用保存，磁盘上的 A 又被 `os.remove` 掉了——**数据双向丢失，不可恢复**。

### 修复思路（代码你自己写）

在 `os.remove` 之后、清空之前，加一个条件判断：被删的是不是**当前正在编辑的会话**。只有是，才清空并重开；不是，就什么都不动。

判断依据：`session_name == st.session_state.current_session`

### 验收

1. 新建会话 A，随便聊两轮
2. 侧边栏点开历史，加载会话 B（确保存在另一个会话文件）
3. 删除 B
4. **A 的对话内容应当原封不动地留在屏幕上**，且 A 的 json 文件仍在
5. 再删 A 本身 → 屏幕清空，正常

## 0-B　`app.py:186-188` rerun 重复

```python
if st.button(..., key=f"delete_{session}"):
    delete_session(session)
    st.rerun()          # ← 第二个
```

`delete_session()` 内部第 68 行已经调过 `st.rerun()`。Streamlit 的 `rerun()` 是靠抛异常实现的，执行到内部那次就会中断当前脚本，外部这行**永远不会被执行**。

不影响功能，但会误导读者。删掉外部那次，让 `rerun` 的职责收在 `delete_session` 里——**每个函数只负责自己的重绘**。

# Step 1 · 语料加载器

## 目标

新建 `rag/load_docs.py`，提供一个函数：把 `data/docs/` 下 44 篇 Markdown 读进来，拼成**一个字符串**，每篇前面带来源标注。

## 原理：为什么要拼成一个字符串

现在的调用是：

```python
client.chat.completions.create(
    model=...,
    messages=[
        {"role": "system", "content": system_prompt.format(...)},
        *st.session_state.messages
    ],
    stream=True,
)
```

`messages` 是一个列表，每一项都是一条独立消息。"全量注入"最朴素的做法，就是把全部语料**接在系统提示词后面，仍然作为一条 system 消息**。

不拆成 44 条消息的理由：
- 44 条消息会产生 44 组 role 分隔 token，白白浪费
- 来源标注用 Markdown 标题即可表达，不需要消息边界
- 单条长 system 消息的前缀最稳定，最容易命中下面讲的 cache

## 原理：为什么顺序必须固定

**这是 P0 里最值钱的一个知识点，务必理解。**

大模型处理一次请求分两个阶段：
- **prefill**：把你的输入全部读一遍，算出中间状态（KV cache）——这一步的耗时和成本随输入长度线性增长
- **decode**：逐字生成回复

如果两次请求的前缀完全相同，前 K 个 token 的 prefill 结果可以**直接复用**，不必重算。这就是 prefix cache（各家的名字不同，DashScope 叫上下文缓存，机制一致）。

你的语料是固定不变的，天然适合吃这个红利。但有一个前提：**每次请求拼出来的字符串必须逐字一致。**

而 `glob.glob()` **不保证返回顺序稳定**——它依赖文件系统返回目录项的次序。如果哪次顺序变了，21k token 的 cache 全部失效，你每一轮都在付全量 prefill 的钱，而且看不出原因。

所以：**必须 `sorted()`。**

同样道理，来源标注里不要塞时间戳、不要塞随机会话名。任何会变的东西都别放进这条 system 消息。

> 面试可以这么讲：我做全量注入时最关心的一件事是让前缀可缓存——所以语料顺序必须固定、语料内容必须放在消息列表最前、且不能混入任何动态字段。这三件事决定了这个方案的成本是线性可控还是失控。

### 2. 关键的三处（最容易写错）

| 位置 | 要求 | 漏了的后果 |
|---|---|---|
| 取文件列表后 | 必须 `sorted()` | cache 随机失效，成本和延迟上去了还查不出原因 |
| 来源标注格式 | 统一为 `【来源：百科-柚子】`，用**文件名去掉 `.md`** | 后面做归因分析和 BM25 时没法对照 |
| 编码 | `encoding="utf-8"` | Windows 下默认编码可能不是 utf-8，中文直接乱码或抛异常 |

### 3. 路径不要写死

`app.py` 第 10 行已经给了正确示范：

```python
SESSIONS_DIR = os.path.join(os.path.dirname(os.path.abspath(__file__)), "data", "sessions")
```

用 `__file__` 解析，而不是写死 `E:/guoxiaomi/...`。`load_docs.py` 在 `rag/` 下，需要往上退一级再进 `data/docs`——用 `os.path.dirname()` 套两次，或者 `os.path.join(..., "..", "data", "docs")`。

写死绝对路径的后果：换台机器、换个盘符就全崩。

# 后面几步（先不要动手）

## Step 2 · 注入 app.py

三个要点，到时候展开：

1. **只读一次**。用模块级变量或 `st.cache_data` 缓存，不要每轮对话读 44 个文件。
2. **绕开 `.format()`**。当前语料里花括号数为 0，所以直接拼进去不会炸；但只要以后加一篇带 `{` 的文档，`.format()` 立刻抛 `KeyError`，而且报错位置离病因很远。现在改成本是 0。建议改用 `str.replace()` 填 name/character，原理一句话就能讲清，也不会误伤任何字符。
3. **语料放在 messages 最前面**，紧接系统提示词之后。

## Step 3 · 历史截断

`app.py:213-218` 现在是 `*st.session_state.messages`（全量历史）。注入 21k 语料后，可用上下文变成 `21k + 历史`，留给对话的空间被压掉一半。至少先做 `history[-N:]`。

## Step 4 · 评测集

8–10 题，覆盖百科 / 配送 / 售后 / 优惠 / 会员各类别，改前改后各跑一遍。

三个评分维度：
- **是否拒答**（"暂时没有资料"话术的出现率）
- **事实正确性**（对照语料原文人工判）
- **约束是否退化**（重点！见下）

第三个维度务必加上，这是全量注入最容易被忽略的副作用：**21k 语料塞进去之后，原来那些 Constraints（禁用绝对化用语、健康类加免责、不越权承诺）还守不守得住？** 长上下文存在"中间信息被稀释"的现象，规则可能被冲淡。检测方法：故意问"这水果能保证绝对新鲜吗""我能保证明天到吗"，看它是否仍拒绝。

**如果注入后拒答率降了但约束也崩了，那这个方案是有代价的——这个发现本身比一个漂亮的数字更有价值。**
