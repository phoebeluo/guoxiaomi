## 二、4 张表为什么是 4 张

最省事的做法是一张表两列：`name` + `payload TEXT`。**但那样等于没迁**——
能做的操作还是「整份读、整份写」，和 JSON 文件一模一样。拆表的依据是**访问模式不同**：

| 表 | 写入时机 | 访问模式 | 拆出去的理由 |
|---|---|---|---|
| `sessions` | 每轮更新 | 列表页频繁扫 | 列表页只要名字/时间/条数，不该把整段正文读出来 |
| `messages` | 每轮追加 | 按会话顺序读 | 1:N，且需要 `(session_id, turn_no)` 唯一约束防重复写 |
| `tool_calls` | 工具触发时 | 按消息回查 | 一条回答可能调**多次**工具，塞不进固定列 |
| `llm_usage` | 每次调模型 | 按月聚合算成本 | 与消息不同步：重试会让一次回答对应多条用量 |

`tool_calls.arguments` / `result` 用 JSON 字符串存，没有拆列：3 个工具的参数结构互不相同，
拆列等于给每个工具建一张表，而工具是会增删的。**这里的「不规范」是有意的**。

## 三、两个 SQLite 的坑（面试可讲）

1. **外键默认是关的。** `PRAGMA foreign_keys` 默认 OFF，是 SQLite 的历史包袱。
   不显式打开，建了 FK 也不生效，删会话不会连带删消息，库里会慢慢长孤儿行。
   而且它是**连接级**开关，连接池复用的每条新连接都要重设——
   只在启动时设一次，bug 会在池子换连接后才出现，本地测不出来。
   实现：`db/__init__.py` 用 `event.listens_for(engine, "connect")` 挂 PRAGMA。
2. **WAL 模式。** 默认 rollback journal 下写事务阻塞读事务，列表页撞上正在写的问答就会等锁。

## 四、事务边界：为什么必须一个事务

一次完整问答 = 1 条 user 消息 + 1 条 assistant 消息 + N 条工具调用 + 1 条用量
+ 更新 `updated_at` / `message_count`。分开提交就会留下「有提问没回答」的会话。

原来的 JSON 方案用**整份重写**掩盖了这个问题——不会出现半条消息，但代价是
**第 n 轮要把前 n-1 轮全部重写一遍（O(n) 写放大）**。这是迁移真正的收益点，
也是「为什么不用 JSON 列」的答案。

## 五、迁移怎么保证不出事

1. **幂等**：默认跳过库里已存在的会话。脚本会被反复执行，不幂等就会写成两份。
2. **dry-run 先看数**：先知道「几个会话、多少条、有没有解析失败」再写库。
3. **不删源文件**：只复制进库，JSON 原样保留。删源是独立的下一步，得等库核对完。

实测（`data/sessions/` 5 个文件）：

```
可迁移   : 5 个会话 / 32 条消息
迁移完成 : 写入 5 / 跳过 0 / 失败 0
库内统计 : {'sessions': 5, 'messages': 32, 'tool_calls': 0, 'llm_usage': 0}
复跑     : 写入 0 / 跳过 5 / 失败 0      ← 幂等
```

## 六、上层零改动的切换方式

`app.py`（Streamlit）和 `api.py`（Flask）共用 `core` 的 4 个会话函数，
所以只改了这 4 个函数：`SESSION_BACKEND=json|db` 决定走哪套实现，
**返回结构、异常类型完全一致**（`FileNotFoundError` → `/sessions/<id>` 的 404 靠它）。

验证（`SESSION_BACKEND=db` 下跑 Flask test client）：

```
/sessions        -> 200  ['2026-10-29 22-55-37', ... 共 5 个]
/sessions/<id>   -> 200  keys=['character','current_session','messages','nickname'] msgs=6
/sessions/不存在  -> 404
```

## 七、测试

新增 `tests/test_db.py` 12 条，测的是**数据库带来的东西**，不是「能不能读写」：

| 类别 | 用例 |
|---|---|
| 结构 | 4 张表存在、`ix_message_session_turn` 索引存在、`PRAGMA foreign_keys` 真的是 1 |
| 级联 | 删会话连带删 messages/tool_calls/llm_usage；删不存在的返回 False |
| 事务 | 工具调用写失败 → 本轮两条消息也不落库（原子性）；同轮次重复写报 IntegrityError |
| 等价 | 返回结构与 JSON 完全同形；覆盖不追加；列表倒序；缺失抛 FileNotFoundError |
| 分发 | `core` 切 db 后跑原来 json 后端的不变式 |

全量：**124 passed**（原 112 + 新 12）。

## 八、已知边界（必须自己讲清楚，不许含糊）

1. **是 SQLite，不是 MySQL。** 本机没有 MySQL（`where mysql` / `where mysqld` 均无）。
   计划里的退路即「SQLite 完成 A/B/C，简历写 SQLite（可迁移 MySQL），不写熟悉 MySQL」。
   换成 MySQL 需要改的只有 `db/__init__.py` 里的连接串（ORM 层不感知方言）。
2. **`tool_calls` / `llm_usage` 当前是 0 行。** 历史 JSON 里只存了 role/content，
   没有工具调用和用量记录。这两张表是**为增量写入准备的**（`store.append_turn`），
   新链路接上才会有数据。**不得说成「已落库」**。
3. **增量路径还没接到主链路。** `app.py` 交出来的是整份 `messages`，
   它不知道「这轮新增了哪几条」，所以目前仍走覆盖语义。
   接增量需要先改 Streamlit 的状态管理，属独立改动。
4. **没做写入性能对比。** 迁移的收益（O(n) → O(1)）是**结构性论证**，
   没有实测数字支撑（5 个会话 32 条消息，测了也没有统计意义）。
   面试若被问「快了多少」，回答「没测，量太小；但写放大从 n 降到常数是可推的」。
