## 一、现状

`app.py:236-239`（当前真实行号）：

```python
        messages=[
            {"role": "system", "content": system_content},
            *st.session_state.messages      # ← 全量历史，有多少发多少
        ],
```

`st.session_state.messages` 的长度只增不减（`app.py:225` 每轮 append，`app.py:255` 每轮存盘）。对话越长，每轮请求携带的历史越多。

---

## 二、诚实的价值评估（先看这个，再看怎么做）

**别把这一步想得太重要。** 量化一下你项目的实际情况：

| 组成部分 | 大小 | 是否会增长 |
|---|---|---|
| system + 语料 | 约 21,000 tokens | **固定**（且顺序不变，可命中 prefix cache） |
| 历史消息 | 每轮约 100–300 tokens | **唯一无限增长的部分** |

按 20 轮对话算，历史约 **2,000–6,000 tokens**，相对 21k 的固定语料占 **10%–22%**。

**结论**：在你这个项目的实际对话长度下，截断省下的成本很有限，也不会撞上上下文上限。**这一步的真正价值是两条**：

1. **防御性设计**——上线后遇到话痨用户或让用户粘贴长文，不会突然爆掉
2. **面试叙事**——"我考虑过上下文预算"是一个有经验的开发者才会有的意识

**所以讲的时候要诚实**：不要说"优化后成本降低 90%"，那是假的。要说"这一步在当前规模下收益有限，但它是防止异常输入击穿上下文的安全边界"。

> **这句话本身就是加分项**——面试官见过太多把 1% 改进吹成 10 倍提升的候选人，能准确说出"这个优化什么时候有用、什么时候没用"的人反而更可信。

## 三、三个方案（选一个，但要能讲清为什么不选另外两个）

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 按条数截断** | 保留最近 N 条消息 | 一行切片，零依赖 | 一条超长消息（用户粘贴长文）就能打破预算 |
| B. 按 token 估算 | 从尾部累加，直到超过 token 上限 | 预算精确可控 | 要引 tokenizer 或写估算函数；中文 token 估算容易算错 |
| C. 摘要压缩 | 把旧对话让模型总结成一段话，替换原历史 | 保留远期信息又不占空间 | 每轮多一次 LLM 调用，延迟与成本都上升 |

**本项目选 A。** 理由：当前对话都是短句，条数上限足以覆盖；B 的收益不足以抵消复杂度；C 需要额外调用，成本反而更高。

## 四、你要写的东西（三处）

### 改动 1 · 顶部加一个常量

放在 `app.py` 的 `SESSIONS_DIR` 附近（第 12 行下方）：

```python
MAX_HISTORY = 10
```

`10` 是"最近 10 条消息"≈ 5 轮完整对话。

### 改动 2 · 加一个函数

放在 `app.py` 上部的函数区（和 `generate_session_name` 同一区域）。

**函数要求**（自己写实现，别直接抄）：

```
名字：recent_messages
参数：messages（历史消息列表）、max_count（最多保留几条）
返回：一个列表，满足两个条件
      ① 长度不超过 max_count
      ② 第一条必须是 role == "user"
做法提示：先切片取尾部，再从左端逐条丢弃，直到开头是 user
```

**三个坑，必须自己踩对**：

**坑 1 · 切片可能切在 assistant 上。** 现场演示：

```
共 8 条消息（4 轮对话）
天真写法 messages[-3:] →
    assistant | 第3轮回答      ← 以 assistant 开头，对话结构断裂
    user      | 第4轮提问
    assistant | 第4轮回答

修法（向左推进到 user 开头）→
    user      | 第4轮提问
    assistant | 第4轮回答
```

为什么要在意：正常对话是 `user → assistant → user → assistant` 交替。以 `assistant` 开头，语义上是"模型上句话没头没尾"，严格的接口实现会直接报错。

**坑 2 · 判据用 `role != "user"`，不要用"长度是偶数"。**
如果某次请求中途失败，历史里可能出现连续两条 `user`（用户的下一句紧跟着上一句，中间没有 assistant 回复）。按长度判断会错位。

**坑 3（最危险）· 不要直接改动 `st.session_state.messages`。**
切片写法 `tail = messages[-max_count:]` 返回的是**新列表**，对 `tail` 做 `pop(0)` 是安全的。
但如果你写成 `while messages[0]["role"] != "user": messages.pop(0)`——**那会把用户的真实历史永久删掉**。这个 bug 不会报错，只会在用户下次打开会话时发现"我前几轮说的话没了"。

### 改动 3 · 换掉调用点

`app.py:238`：

```python
            *recent_messages(st.session_state.messages, MAX_HISTORY)
```

**保持 system 消息在最前不动**——这点很重要，见第五部分。

## 五、为什么截断不会破坏 prefix cache（关键理解）

你可能担心：我一直在做前缀缓存，截断历史会不会把它弄失效？

**不会。** 因为：

```
messages = [
    {system + 21k 语料}     ← 前缀，固定不变，缓存命中区
    ...截断后的历史...        ← 变化区，在后面
    {当前用户提问}           ← 变化区，在最后
]
```

prefix cache 匹配的是**从第 0 个 token 开始的最长公共前缀**。system 那段始终完整地在最前面且内容一致，所以缓存照常命中，只是"公共前缀"到 system 结尾为止。

**反面情形**：如果你哪天为了"最新消息优先"把历史提到 system 前面，整个缓存立刻全废——**每轮都要为新顺序重新 prefill 21k tokens**。所以顺序是刚性约束：**system → 旧历史 → 新历史**。

## 七、面试要点

### 7.1 可以讲的核心（必背）

**"上下文预算是有限资源，我把它分成固定成本和可变成本两块管理。"**

- **固定成本**：21k 的 system + 语料。它的优化手段不是砍掉，而是**让它可被前缀缓存复用**——顺序固定、放最前、不混入动态字段。
- **可变成本**：历史消息。它才是真正需要设上限的部分，因为它是唯一无限增长的。

这个"分清固定/可变、分别用不同手段优化"的思路，比具体代码更能体现工程判断力。

### 7.2 会被追问的三个问题

**Q：为什么按条数截断，不按 token？**
答：按条数一行切片、零依赖；按 token 要引 tokenizer，而且中文 token 估算容易出错。我的对话场景是短句交流，条数上限足以控住预算。**如果换成用户会粘贴长文本的场景，我会改成按 token 累计截断。**

**Q：为什么不干脆只发最近一轮，最省 token？**
答：多轮对话的价值在上下文连续性——用户说"那第二个呢"、"换成送人的"这类指代，全靠历史才能理解。截断到一轮会立刻丢掉这种能力。**10 条是"保住上下文连贯"和"控预算"之间的折中。**

**Q：截断会不会影响你的前缀缓存？**
答：不会。缓存匹配的是从第 0 个 token 起的最长公共前缀，而 system（含语料）始终在最前且内容不变，所以缓存照常命中；被截断的是它之后的历史段。**反过来说，如果我把历史放到 system 前面，缓存就全废了。**

### 7.3 一条红线

**不要说"做了历史截断，成本显著下降"。** 在你 20 轮以内的对话规模下，这几乎测不出差别。如实说：

> 这一步在当前规模下收益有限，它的作用是防止异常输入（超长对话、粘贴长文本）击穿上下文，属于防御性边界。

**能准确说出一个优化"什么时候有用、什么时候没用"，比夸大战果可信得多。**
