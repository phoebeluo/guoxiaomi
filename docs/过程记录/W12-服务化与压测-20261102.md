## 一、为什么必须抽 core.py

抽之前，`app.py` 第一行是 `import streamlit`。要加 HTTP 接口只有两条路：

| 路 | 后果 |
|---|---|
| 在 `api.py` 里复制一遍检索 + 拼 prompt + 调模型 + 存会话 | 两份代码各自漂移，改一处忘一处 |
| 让 Flask 也 `import streamlit` | 把一个 UI 框架拖进服务端进程 |

所以抽 4 个函数（计划里只允许抽 1 个文件，不许拆六模块）：

| 函数 | 职责 |
|---|---|
| `retrieve` | 按 `RETRIEVAL` 档取 top-k 篇 |
| `build_system_message` | 拼 system，返回来源名单 |
| `call_llm` | 流式 / 非流式两种入口 |
| `save_session` / `load_session` | 会话落盘 |

**不抽**：UI、状态管理、控件。那些是 Streamlit 强绑定的，抽出来只是假抽象。

守边界的方式是一条测试，不是自觉：

```python
def test_core_does_not_import_streamlit():
    ...  # 用 AST 扫 import
```

用 AST 扫而不是 `assert "streamlit" not in sys.modules` —— 后者会被「别的测试先 import 了 streamlit」污染，永远为真。

## 二、提示词从「两份副本」变成「一个来源」

抽 core 时发现一个更隐蔽的问题：**提示词原本有两个副本**。

| 位置 | 谁在用 |
|---|---|
| `app.py` 里的 `system_prompt = """..."""` | 线上 |
| `tools/eval_run.py` 里 `_load_system_prompt()` 用正则**从 app.py 抠** | 离线评测 |

第二份靠正则从第一份抠，看起来「自动同步」，实际很脆：只要有人把提示词搬进函数或常量，
抠取就会静默失败或抠到半截。而 `tools/check_prompt.py` 只比对几个锚点字符串，
**改了一句话、锚点没动，两份就悄悄不一致了**。

11-02 加「工具结论高于顾客口述」时正好踩到这点：差点只改一处。
那意味着**评测用的 prompt 和线上跑的 prompt 不是同一份，所有指标瞬间失去意义**。

改为 `rag/prompt.py` 里的 `SYSTEM_PROMPT` 常量，三处一起改：

| 文件 | 改法 |
|---|---|
| `app.py` | `system_prompt = SYSTEM_PROMPT` |
| `tools/eval_run.py` | 正则从 `rag/prompt.py` 读 `SYSTEM_PROMPT = """..."""` |
| `tools/check_prompt.py` / `tools/check_injection.py` | 目标文件同步换成 `rag/prompt.py` |

**同步从此由结构保证，不靠人记得。**

## 三、Flask 接口：三个决定

| 决定 | 理由 |
|---|---|
| `MAX_INFLIGHT=8` 信号量 + 503 + `Retry-After` | 上游 RPM 有配额，主动拒绝比让请求在上游超时好。用户 200 ms 就知道要重试，而不是等 30 秒拿 504 |
| 单进程、threaded | 多进程会把信号量复制成 N 份，`MAX_INFLIGHT` 立刻失去意义；压测要测的是「一个 worker 扛多少」 |
| 不吞异常 | 压测必须能区分 5xx（我的锅）和 503（限流的锅）。全包成 200，错误率永远 0，那种压测没有意义 |

接口：

```
POST   /chat              一次问答，返回 answer / sources / tools / usage
POST   /chat/stream       SSE 流式
GET    /sessions          会话列表        GET /sessions/<id>   详情
DELETE /sessions/<id>     删除            GET /health          探活
```

## 四、压测：为什么必须 mock 模型

真调模型压测会得到一个「P99 = 3.2 s」的数字，然后谁也说不清这 3.2 秒里
多少是我的代码、多少是阿里的排队。所以 `MOCK_LLM=1` 用假模型（固定 50 ms），
**测服务层，把上游变量摘掉**。

| 并发 | QPS | P50 | P95 | P99 | 200 | 503 | 备注 |
|---|---|---|---|---|---|---|---|
| 1 | 16.0 | 57 ms | 81 ms | 82 ms | 40 | 0 | 单并发基准：一次请求 62 ms |
| 4 | 62.0 | 59 ms | 79 ms | 81 ms | 40 | 0 | 线性放大，尾延迟不动 |
| 8 | **109.8** | 60 ms | 77 ms | 79 ms | 40 | 0 | **峰值**，与 `MAX_INFLIGHT=8` 对齐 |
| 16 | 83.3 | 76 ms | 79 ms | 80 ms | 12 | 28 | 一半以上被 503 挡住 |
| 32 | 97.1 | 74 ms | 90 ms | 91 ms | 13 | 27 | 再压只增加拒绝，不增加吞吐 |

> 两次运行峰值 109.8 与 113.5，波动约 ±3%（Windows 本机、单进程）。
> 引用时给区间，不给单点——单点数字看起来精确，其实只是恰好那一次。

**拐点在并发 8–16**：并发放到 8 时 QPS 已到 110（≈ `8 / 50 ms` 的理论值），
再往上 QPS 不涨、P50 从 60 → 76 ms，同时 503 开始出现——加并发只换排队。

关键不是「113 QPS」这个数，而是**它为什么停在这里**：

| 层 | 单次开销 | 是不是瓶颈 |
|---|---|---|
| 检索（45 篇向量余弦） | 约 4 ms | 否 |
| 拼 prompt + 落盘 | 3–8 ms | 否 |
| **模型生成** | **数百 ms ~ 数秒** | **是** |

理论峰值 = `MAX_INFLIGHT / mock延迟` = 8 / 0.05 = 160 QPS，实测 110（框架、序列化、落盘吃掉约三成）。
**吞吐上限是我自己设的，不是硬件逼出来的** —— 这个数该由上游 RPM 决定，不该由 worker 数决定。

所以结论是：并发保护做在入口，而不是拼命加 worker。加 worker 只会让更多请求
同时卡在上游等待，把 429 变成超时。

> 面试口径：「我的 QPS 上限不在我的服务，在上游 RPM。这件事本身就是结论——
> 客服系统的吞吐瓶颈通常不在应用层，所以我把限流做在入口（信号量 + 503 + Retry-After），
> 而不是加 worker。」

## 五、压测抓到一个真 bug（这一节比压测数字值钱）

第一次压测，并发 8 时 **40 个请求里有 4 个返回 400**。查下来是一条完整的因果链：

1. 没传 `session_id` 时，会话名 = `datetime.now():%Y-%m-%d %H-%M-%S`，**只精确到秒**
2. 同一秒进来的 4 个并发请求，拿到**同一个会话名**
3. 于是 4 个线程同时读-改-写同一个 json
4. 一方读到另一方写了一半的文件 → `JSONDecodeError`
5. `JSONDecodeError` 是 `ValueError` 的子类，被 `except ValueError` 捕获 → 返回 **400 bad_request**
6. 于是「我的并发 bug」被伪装成「客户端乱传参数」

第 5 步是这次最值得记的一课：**异常继承顺序会把服务端 bug 报成客户端错误**，
现场看到 400 第一反应一定是「压测脚本写错了」，方向就偏了。

三处修法：

| 修法 | 内容 |
|---|---|
| 会话名唯一 | 时间戳 + 6 位 `uuid4` 后缀，可读性保留、唯一性补上 |
| 写锁 | 每个会话一把 `threading.Lock`，读-改-写整段互斥（否则并发下会丢轮次） |
| 异常顺序 | `except json.JSONDecodeError` 排在 `except ValueError` **之前**，返回 500 |

修完重跑，400 归零、500 归零，`test_session_ids_are_unique_under_concurrency`
（16 并发断言 id 全不重复）锁住它。

> 一句话：**压测的价值不在 QPS 这个数，在于它能在你本地跑不出问题的地方跑出问题。**
