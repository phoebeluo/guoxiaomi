# W9 · 三个可兑现的工具（2026-11-02）

> 目标：把「我帮您查一下」这句话第一次变成真的。
> 产出：`agent/tools.py`（schema + 3 个工具 + 参数校验）、`tests/test_tools.py`（23 项）。
> 零 API：全部是本地单测，没有调用模型。

---

## 一、能力清单：只做「系统真能兑现」的三件

| 工具 | 回答什么问题 | 数据来源 |
|---|---|---|
| `check_delivery` | 能不能送到我这 / 多久到 / 运费多少 | `配送-服务城市与区域.md`、`配送-范围与时效.md`、`配送-运费与包邮门槛.md` |
| `calc_member_level` | 我是什么会员 / 怎么升级 / 还差多少 | `会员-等级与权益.md` |
| `query_order_status` | 我的订单到哪了 | 本地 fixture（`ORDERS`），W12 换真实订单库 |

**三个工具的事实表是从语料抄过来的，不是另写一套。** 有 3 条单测专门读语料原文校验名单与数字，
防止「工具说满 2000 升金卡、知识库说满 3000」这种最难查的漂移。

## 二、排除清单：五个能力**明确不做**（W9 第二天）

| 不做 | 理由 |
|---|---|
| **转人工** | 没有工单系统与坐席排班。做了就是假装能转接，正确做法是给「我的 → 联系客服」路径 |
| **实时物流** | 没有承运商接口。编一句「已到达成都转运中心」比不回答更糟 |
| **赔付审批** | 涉及资金与凭证核验，必须人工。机器只能说明政策与所需材料 |
| **库存查询** | 无实时库存源，假数据会诱导「有货」承诺（计划已删） |
| **优惠券试算** | 依赖用户券包，无数据源只能编造可用券（计划已删） |

> 这条判断比工具本身值钱：**做工具的目的是消灭虚假承诺，不是让功能变多。**
> 后四个都能做出来「看起来能用」，但每一个都是新的虚假承诺。

`EXCLUDED` 已写进代码常量，并有单测断言「排除清单里的能力不许出现在工具里」。

## 三、Schema 设计：约束写进 schema，代码只做兜底

三个工具都用 OpenAI function calling 格式，关键约束**写在 schema 里**而不是只写在代码里：

| 约束 | 写法 | 为什么 |
|---|---|---|
| 必填 | `required: ["district"]` | 模型看到 required 才会主动追问缺失参数 |
| 取值范围 | `member_level` 限定 `1–4` | 越界值模型自己就不会给，代码校验是第二道 |
| 格式 | `order_id` 给 `pattern: ^GXM\d{11}$` | 让模型知道「订单号长什么样」，减少乱猜 |
| 关闭自由发挥 | `additionalProperties: false` | 防止模型自创 `user_id` 这类字段 |
| 单位说明 | `order_amount` 描述里写「订单实付金额（元）」 | 不写清单位，模型会把「79」当分 |

**代码里的 `_validate()` 是兜底**，不是主防线。模型仍可能给越界值，那时必须能明确拒绝。

### 六个错误码（评测要用字段，不能用句子）

| 码 | 触发 |
|---|---|
| `MISSING_ARG` | 缺必填参数 |
| `UNKNOWN_ARG` | 塞了 schema 里没有的字段 |
| `BAD_TYPE` | 类型不对（如 `"两千"` 传给 number） |
| `BAD_VALUE` / `OUT_OF_RANGE` | 超范围、超长度、不在枚举内 |
| `BAD_FORMAT` | 订单号格式不对 |
| `ORDER_NOT_FOUND` / `UNKNOWN_TOOL` | 查不到订单 / 编造工具名 |

为什么用错误码而不是错误句子：W11 的「越权拒绝率」要统计，句子没法统计。

## 四、两个设计取舍（都被单测锁住）

### ① 行政区名要规范化

用户会说「武侯」「武侯区」「成都市武侯区」。直接字符串相等会把前两种判成**不配送**——
那是工具自己制造的误判，而且用户会觉得「明明在成都你说送不到」。

处理：去掉「成都市/成都」前缀，缺后缀的补「区」。单测：`check_delivery("武侯")["district"] == "武侯区"`。

### ② 查不到订单必须显式报错，不能返回空对象

返回 `{}` 会让模型以为「查到了但没内容」，然后自己编一个状态。
所以 `query_order_status` 查不到就抛 `ToolError("ORDER_NOT_FOUND")`，
经 `safe_dispatch` 转成 `{"ok": false, ...}` 回给模型，让它老实说「这个单号查不到」。

**这是整个 W9 里最容易做错的一处：静默失败会变成编造。**

## 六、对话循环接入 `app.py`（W9 第六天）

新增 `agent/loop.py`，`stream_chat()` 是生成器，产出三类事件：`delta`（正文增量）、
`tools`（本轮工具调用与结果）、`usage`（多轮累加）。

四个设计决定：

| 决定 | 为什么 |
|---|---|
| **首轮就开流式**，不做非流式探路 | 绝大多数提问不需要工具。为少数情况牺牲全部提问的流式体验，等于用 90% 的体验换 10% 的功能 |
| **按 `index` 拼装 `tool_calls` 分片** | OpenAI 兼容协议里 `name` 与 `arguments` 是分片下发的，多工具并发时顺序会交错，不能按到达顺序直接拼 |
| **最后一轮撤掉 `tools`** | 否则模型可能反复调工具不收敛。收敛条件是「回合数用完」，可控性优先 |
| **工具结果原样 JSON 回灌**，不改写成自然语言 | 改写会在「工具说了什么」和「用户看到什么」之间加一层没有测试覆盖的中转；W11 要统计参数正确率，必须拿到原始字段 |

`TOOLS=on/off` 环境变量开关，与 `RETRIEVAL` 同规矩：启动即定，用于 A/B。

### 零 API 验证：假客户端

`tests/test_agent_loop.py` 9 项，用一个假客户端把「模型返回什么」固定住，只测循环本身：

| 场景 | 断言 |
|---|---|
| 不需要工具 | 只调一次、正文拼接正确、首轮带 tools |
| 参数分片 | `{"order_` + `id":"GXM..."}` 能拼成合法 JSON 并真的查到订单 |
| 回灌格式 | messages 末尾是 `assistant(tool_calls)` + `tool(tool_call_id)`，且 content 是 JSON |
| 工具报错 | `ORDER_NOT_FOUND` 原样回灌给模型，不被吞掉 |
| 编造工具名 | `refund_approve` → `UNKNOWN_TOOL`，不崩 |
| 参数不是 JSON | `BAD_JSON`，不崩 |
| 轮次上限 | `max_rounds=2` 时只调两次 |
| 用量累加 | 两轮 50+70 = 120 |

**为什么用假客户端而不是真调 API**：真调一次 2 分钟 + 烧额度，而且出错时分不清是模型没调对还是代码写错。
把「模型返回」固定住，剩下的全是可复现的纯逻辑。

### 一个必须解决的冲突：拒答规则会抢在工具前面

`rag/refusal.py` 原来的第一条规则是「查订单物流」，正则会拦住「我的订单到哪了」——
**这句话现在工具能回答了，但用户在规则层就被推开了，工具永远调不到。**

修法：规则收窄为「查物流轨迹」，只拦**物流轨迹**（真的没有承运商接口），
订单状态放行给模型（它会反问单号，再调 `query_order_status`）。

复测：库外 6 题仍拦住 **3 题**（#8 #9 #15），**误拒仍是 0/54**，只有「我的订单到哪了」从拦变放行。

> 这个冲突本身是个好素材：**加能力不是加代码，是改边界。** 新工具会跟旧规则打架。
