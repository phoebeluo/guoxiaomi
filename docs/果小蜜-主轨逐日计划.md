>
> ⚠️ **诚实标注（2026-10-28）**：TF-IDF+SVD **不是 embedding**。JD-14 原文要「精确和近似的最近邻搜索、

| 32 | 六模块拆层（3 h）→ **1 个 `core.py`**（0.5 h） | W12 | 2 h | 分层是「工程规范」需求，**Flask 只需 import 四个函数**；六模块不产生任何数字 |

**另修两处非删除项**

| 类型 | 内容 |
|---|---|
| 🔴 **顺序错误** | **引用出处从 W8 前移到 W5**。它会改 prompt，放在 W7 之后会作废 W7 刚花 0.12M token 跑出的三策略数字（纪律：改 prompt 必须重跑）。前移后 W7 跑的就是最终 prompt |
| 🔴 **额度风险** | W13 全量重跑需 52 题 × 2 ≈ **0.56M**，而剩余免费额度约 **0.44M** —— 跑不起。改为只重跑受 badcase 影响的 **10 题子集**（≈0.11M） |

**净变化**：34 → **28 h**；自然周 **6 → 5**；终点 **12-25 → 12-18**。

> **这一轮删的东西有个共同点**：它们都不是「做错了」，而是「做了也不改变任何数字」。
> 判断方法很土 —— 问一句「删掉它，简历会少一句吗？」不会，就删。


**三类"看起来重要、其实零贡献"的模式**（以后自查用）：

1. **中间态方案**——被后续方案完全取代（类别路由被 BM25 取代）。留着不加分，还会让面试官怀疑你不清楚系统分层。
2. **为"完整"而做的收尾项**——审批门 / Compose / 帕累托图 / 外部校准。证明工程完备性，但没有一个面试官会问「你写过 Compose 吗」。
3. **数量型自我安慰**——5 个工具 / 20 条用例 / 20 条对抗 / 1000 篇档。**"3 个工具 + 每个能讲 3 层设计理由" > "5 个工具 + 都说跑通了"**。

## 六、并行轨：M14 后端（本轨之外，但同等重要）

> **为什么单开一条轨**：果小蜜的 RAG、评测、Agent 做到什么程度，都补不上「数据库 + Web 后端」这一格。
> 17 条 JD 里 M14 出现 **11 次**；**6 条成都实习里 MySQL 5 次、Django/Flask 3 次**，而现状是 **L0**。
> 这是唯一「不补就投不进去」的项，但它与果小蜜技术栈无关，所以**必须并行、不能塞进主轨消耗主轨的 32 h**。

| 阶段 | 内容 | 产出（要能写进简历的一句话） | 成本 |
|---|---|---|---|
| **A. 数据库** | 建表 / 主外键 / 索引 / 增删改查 / 事务；SQLite 起步再迁 MySQL | 「设计 4 张表的客服会话库，含索引与事务」 | 3 天 |
| **B. ORM + 接口** | SQLAlchemy（或 Django ORM）+ **Flask** 提供 4 个 REST 接口 | 「Flask + ORM 实现会话 CRUD 接口」 | 3 天 |
| **C. 接进果小蜜** | `data/sessions/*.json` → 关系库 | 「会话持久化由 JSON 落盘迁移到关系库」 | 2 天 |

**关键：C 阶段必须做。** 纯教程式的建表练习在简历上没有位置；把果小蜜的会话存储真迁到数据库，
才是「我用数据库解决过一个真实问题」。这也是主轨 W12 拆层的直接收益 —— **拆完才能换存储**。

**与主轨的耦合点**：W12（Flask 化）与 B 阶段共用同一个 Flask 骨架；W5（检索接入）→ W7（三策略）期间并行推 A/B。

**卡点**：一周内 MySQL 起不来（本机环境问题）就退到 SQLite 做完 A/B/C，
简历写「SQLite（可迁移 MySQL）」，**不写「熟悉 MySQL」**。

## 七、每周固定动作（不可省）

1. **周日必跑评测并归档**；失败运行自动改名 `*_INVALID`，**不得覆盖有效报告**。
2. **任何判据改动必跑** `tools/test_judge.py`；回归样本用**真实回答**固化。
3. **语料冻结后不中途改内容**——否则索引与全部评测作废。
4. **题库定型后不中途加题**——加了就与历史数字不可比；确需加题，**另存版本号**。
5. 每周在 `docs/过程记录/` 留一页：改了什么、数字多少、踩了什么坑。
6. 任何要写进简历的数字，**必须能讲满 3 分钟**；讲不出来的删掉。

## 十、最终产物形态（简历目标）

> 1. **知识库接入对照链**：**无语料 → 理想检索 → BM25 检索**（52 题 · qwen3.7-plus，同口径）；另单列 22 题档的**全量注入 95% vs 理想检索 100%**（qwen3.5-plus，system 33,766 → 5,423）。⚠️ 两档分母与模型不同，**不得合并引用** —— 这本身是「成本决定实验设计」的实例：全量注入 52 题需 **1.76M token**，超免费额度。
> 2. **检索质量随语料规模的实测**：45 → 346 篇（7.7 倍），块级 R@5 恒定 95.8%、MRR 0.851→0.880，**证明规模不是瓶颈**；归因到真正瓶颈——口语↔书面语词汇鸿沟（未召回组 token 覆盖率 13% vs 已召回组 45%）。
> 3. **真实检索 vs 理想检索的量化差距**：C 100% / D 98%，**检索损失 2 pp 且定位到单题**（#6，模型诚实拒答，失效在检索端）。
> 4. **为客服智能体设计 3 个可兑现工具 + 自建 MCP Server**，以工具调用替代「无法兑现的虚假承诺」；同步建立工具选择 / 参数 / 越权拒绝三项评测。**主动砍掉需要假数据的工具，因为假数据等于制造新的虚假承诺。**
> 5. 建立能力边界约束层，区分「模型做不到」与「业务没有」。
> 6. **将评测判据本身作为被测对象**：19 例回归、4 类误判修正 + 新登记 J1/J2，确立「失败运行不得覆盖有效报告」的指标纪律。
> 7. 建立**规模无关**的切分验收标准（平均块长 250–400 + P95 ≤ 450），替代会随扩容失效的「总块数 60–90」。
> 8. 服务化：**Flask** + **QPS/P99 压测**，并定位到「吞吐瓶颈在上游 RPM 而非应用层」。
> 9. **失败归因三分类**：把「未通过」拆成 **模型失败 / 判据失败 / 检索失败**。实测 **6 条判据失败**（#5 #37 #48 #38 已于 10-19 修完、J1 #45 / J2 #15 待修）、**1 条检索失败**（#6）、**0 条模型失败** —— 95% → 100% 全靠改判据，模型一个字没动。见 `docs/过程记录/badcase归因总表-20261028.md`。
