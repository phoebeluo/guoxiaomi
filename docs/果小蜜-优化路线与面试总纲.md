## 四、专题：`--rejudge` 离线重判（四处改动详解）

> 这是本项目**最能体现工程成熟度**的一件小事。本节按「**原因 → 原理 → 原代码 → 新代码**」  
> 逐点拆开，每一点都写到"不懂 Python 也能看懂"的程度。

### 4.0 先看它解决什么问题

**原来的痛点**：每改一次判据（比如 `#12` 的 pattern），想看效果就得跑一遍完整评测  
= **44 次 API 调用**（19 题 × 2 策略，多轮题还要翻倍）。

**但真相是**：

> 改判据**根本不关模型的事**——模型早就答完了，你只是换了一个「评分标准」。  
> **凭什么为了换评分标准，再把额度烧一遍？**

**`--rejudge` 就是**：把上次跑出来的**答案原样取回**，用**新判据**重新打一遍分，重建报告 —— **零 API 调用**。

**实测效果**：重判 10-10 那份报告 → **84% → 95%（18/19）**，一次 API 都没调。

---

### 4.1 改动一 · 把「写报告」抽成独立函数 `write_report()`

#### 【原因】为什么要动它

`run()`（真跑 API）和即将新增的 `rejudge()`（离线重判）**都要产出一份格式相同的报告**。  
如果不抽出来，那段 100 行的"画表格 + 写文件"代码就得**抄两份**。  
抄两份的后果：将来想给表格加一列，你改了 `run()` 里的那份，忘了 `rejudge()` 里的那份  
→ 两份报告格式不一致 → **"文档/代码脱节"的代码版**。

#### 【原理】三个概念

1. **DRY 原则**（Don't Repeat Yourself，"别重复自己"）：  
   同一段逻辑只允许存在**一处**。要复用，就把它变成**函数**。
2. **闭包**：函数内部定义的函数，可以直接"看见"外面那个函数的**局部变量**。  
   原来 `rate()` 定义在 `run()` 里面，它能直接用 `run()` 的 `cases`、`results`、`model`——  
   **不需要通过参数传进来**，直接"顺手拿"。这在只有 `run()` 一个使用者时很方便，  
   但一旦要搬到别处（给 `rejudge` 用），这些"顺手拿"的变量就**不在视野里了**——  
   所以必须把它们**变成参数**，由调用方显式传进来。
3. **重构的定义**：**"不改变行为，只调整代码结构"**。  
   这次就是把代码"搬家"——逻辑一个字都不改，只是从 `run()` 内部搬到外面。  
   验收标准：搬完后 `run()` 跑出来的报告**必须和以前一模一样**（除了新增的 note 行）。

#### 【原代码】它原来长在 `run()` 肚子里

下面这段（节选）原先**在 `run()` 函数内部**，缩进 4 个空格，直接"顺手拿" `cases`/`results`/`model`：

```python
def run(cases, modes, out_path):
    ...
    model = os.environ.get("LLM_MODEL", "deepseek-v4-pro-0813")
    results = {m: {} for m in modes}
    # ... 调 API 的循环 ...

    # ---------- 汇总 ----------
    def rate(mode, kinds=None, turns=None):        # ← rate 是 run 内部的闭包
        rows = [r for c in cases ... for r in [results[mode][c["id"]]]]
        ...
    lines = []
    lines.append(f"- 模型：`{model}`")              # ← 直接用 run 的 model
    ...
    os.makedirs(os.path.dirname(out_path), exist_ok=True)
    with open(out_path, "w", encoding="utf-8") as f:
        f.write("\n".join(lines))
    # ... 写 json、控制台汇总，一直写到函数结尾 ...
```

**要命的点**：这段代码虽然"不碰 API"，但它**物理上长在 `run()` 里**。  
`rejudge()` 想用它，只有两条路：① 整段复制粘贴；② 交参数调它。前者违背 DRY，所以选②。

#### 【新代码】搬出来，成为平级函数

```python

    同一格式的报告。抽出来 = 一份逻辑、两个入口，避免把这段表格代码抄两份。
    """
    # ---------- 汇总 ----------
    def rate(mode, kinds=None, turns=None):
        rows = [r for c in cases ... for r in [results[mode][c["id"]]]]
        ...
    invalid = bool(failures)              # ← 原来在 run() 里算，现在这里自己算
    lines = []
    lines.append("# 评测结果\n")
    if note:                              # ← 新增：出处行（真跑 / 重判 可区分）
        lines.append(f"> 🔁 {note}\n")
    lines.append(f"- 模型：`{model}`")
    ...
```

**逐项对照**：

| 原来                                 | 现在                 | 为什么                    |
| ---------------------------------- | ------------------ | ---------------------- |
| 长在 `run()` 内部                      | 独立函数               | 两个调用方能共用               |
| `cases`/`results`/`model` 靠闭包"顺手拿" | **变成函数参数**         | 出了 `run()` 就看不见了，必须显式传 |
| 没有出处说明                             | 新增 `note=None` 参数  | 报告要能区分"真跑"还是"重判"       |
| `invalid` 在 `run()` 里算             | `write_report` 自己算 | 该函数要自给自足               |

> **小白补充**：`def f(a, b=None)` 里的 `=None` 意思是"**这个参数可以不传**，  
> 不传时它的值就是 `None`（空）"。`note` 就是这样：`run()` 调用时不传（报告不加这行），  
> `rejudge()` 调用时传一句"离线重判，未调用 API"。

### 4.2 改动二 · `run()` 瘦身（删掉重复的那 100 行）

#### 【原因】

报告逻辑已经搬到 `write_report` 了，`run()` 里那份就是**重复拷贝**，必须删。  
不删的话，两份代码会各自演化，将来必然打架。

#### 【原理】职责单一 + 重构的验收标准

- **职责单一**：一个函数只做一件事。删完后 `run()` 只干三件事：  
  **① 调 API 拿答案 ② 失败保护 ③ 把结果交给写报告的人**。
- **重构怎么证明没改坏**：跑一次小评测（比如 `--mode none`），对比报告格式与数字。  
  **行为不变 = 重构成功**；行为变了 = 说明搬家时手抖了。

#### 【原代码】

就是上面 4.1【原代码】里展示的那一整段——从 `# ---------- 汇总 ----------`  
一直到函数最后一行 `print(f"结构化数据：{json_path}")`，**约 100 行**全在 `run()` 里。

#### 【新代码】`run()` 结尾只剩一行调用

```python
    # 报告生成（汇总+表格+明细+写文件）统一交给 write_report，
    # rejudge 走同一个函数 —— 保证「真跑」和「离线重判」两份报告格式完全一致。
    write_report(cases, modes, results, system_lengths, failures, model, out_path)
```

> 注意：`run()` 调用时**没传 `note`**，所以真跑出来的报告不会多出那行 "🔁 …"，  
> 格式和历史报告保持一致。

### 4.3 改动三 · 新增 `rejudge()`（本次的主角）

#### 【原因】

要有一个"**换标准、不换答案**"的通路。没有它，改判据只能重跑 `run()` = 白烧额度。

#### 【原理】"调模型"和"打分"必须解耦

- **调模型**：花钱、慢、有随机性（哪怕 `temperature=0` 也可能抖动）。
- **打分**：免费、快、确定性（同样的答案 + 同样的判据 = 永远同样的结果）。

原来这两件事**焊死在 `run()` 里**：`调模型 → 立刻打分 → 写报告` 是一条龙。  
只要你想"换个判据再看看"，就只能从头再走一遍那条龙 → 重调模型 → 重花钱。

**解耦之后**：

```
                          ┌── 通路①：run()     ── 调模型 → 拿答案 → 打分 → 报告
数据（答案存档在 json）──┤
                          └── 通路②：rejudge() ── 读答案 → 打分 → 报告（不调模型）
```

**数据从哪来？** 你当初写 json 时留了一行注释（`eval_run.py` 原文）：

```python
# answer 一并留档：判据改进后可离线重判，无需重跑 API（省额度）
```

对应代码（`write_report` 里写 json 的部分）：

```python
"detail": {m: {str(i): {"ok": r["ok"], "hits": r["hits"],
                        "refusals": r["refusals"],
                        "answer": r["answer"]}          # ← 每题答案原文，就存这儿
               for i, r in results[m].items()} for m in modes},
```

**所以 `rejudge` 的三步**：读 json 的答案 → 用新判据 `judge()` 重打分 → 交给 `write_report` 出报告。

#### 【原代码】

**没有原代码**——这是新增功能。在它之前，"重判"这件事**在项目里根本不存在**，  
唯一的替代做法是：`python tools/eval_run.py`（重跑，花钱）。

#### 【新代码】全文逐行讲

```python
def rejudge(src_json, cases, out_path):
    """用【当前】cases.jsonl 的判据，给【已有】报告里的答案重新打分。"""
    with open(src_json, encoding="utf-8") as f:
        data = json.load(f)                       # ① 把报告 json 读成一个字典

    if not data.get("valid", True):               # ② 边界：源报告是无效运行
        raise SystemExit(
            f"源报告 {src_json} 是一次「无效运行」（含 API 调用失败），"
            f"里面的答案不可用于重判。请先重跑一次有效评测。")

    modes = list(data.get("detail", {}).keys())   # ③ 策略从源 json 取，不用命令行
    if not modes:                                 # ④ 边界：源报告没有 detail
        raise SystemExit(f"源报告 {src_json} 里没有 detail 字段，无法重判。")

    # ⑤ 边界：题库可能比源报告新 —— 只重判「每个策略都有存档答案」的题
    judgeable, skipped = [], []
    for c in cases:
        cid = str(c["id"])
        if all(cid in data["detail"][m] for m in modes):
            judgeable.append(c)
        else:
            skipped.append(c["id"])
    if skipped:
        print(f"⚠️ 以下题在源报告中无存档答案，已跳过（需重跑 API）：{skipped}")

    print(f"\n{'=' * 66}\n离线重判（不调用 API）\n{'=' * 66}")
    results = {m: {} for m in modes}
    for m in modes:
        for c in judgeable:
            answer = data["detail"][m][str(c["id"])]["answer"]
            ok, hits, refusals = judge(answer, c)     # ★ 全篇最关键这一行
            results[m][c["id"]] = dict(ok=ok, hits=hits,
                                       refusals=refusals, answer=answer)
            print(f"  {'[通过]' if ok else '[失败]'} #{c['id']:<3} {c['q']}"
                  f"    命中={hits if hits else '无'}")

    write_report(judgeable, modes, results, data.get("system_lengths", {}),
                 [], data.get("model", "?"), out_path,
                 note=f"离线重判（**未调用 API**）：判据取自 {os.path.basename(CASES_PATH)}，"
                      f"答案源 {os.path.basename(src_json)}")
```

**关键点逐个拆**：

| 行 | 写法                                             | 大白话解释                                                                                                                                |
| - | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| ① | `json.load(f)`                                 | 把 json 文件内容读成一个 Python 字典 `data`                                                                                                     |
| ② | `data.get("valid", True)`                      | 取 `valid` 这个键；取不到默认 `True`。若为 `False`（那次运行有 API 失败），**拒绝重判**——因为里面存的答案是 `[调用失败] …` 这种垃圾                                              |
| ③ | `list(data["detail"].keys())`                  | `detail` 的键就是"策略名"（如 `none`/`inject`）。**从源里取，不从命令行**——因为源可能只跑过 `inject`，你强行用两个策略会找不到数据                                               |
| ④ | `if not modes:`                                | 源 json 里压根没有 `detail` 字段（老版本报告）→ 直接报错退出                                                                                              |
| ⑤ | `all(cid in data["detail"][m] for m in modes)` | `all(...)` = "**括号里每一条都为真**"。即"这个题号在**所有**策略里都有存档答案吗"。用 `case["id"]` 去查，是因为 json 的键是字符串（`str(i)`，写到 json 时转的），所以比对时也要 `str(c["id"])` |
| ★ | `judge(answer, c)`                             | **全篇最核心的一行**：`answer` 是**旧答案**（从 json 里取），`c` 是**当前** `cases.jsonl` 的题对象。所以你**一改 pattern，这里立刻生效**                                    |
| — | `failures=[]`（在 write_report 调用里）              | 重判不调 API，**不可能**有调用失败，所以传空列表 → 报告天然是"有效"的                                                                                            |
| — | `note=...`                                     | 给报告头部写一行"这份是重判出来的"，避免和真跑的报告混淆                                                                                                        |

**为什么要处理边界 ⑤（最重要的一条）**：  
假设你先跑了 19 题的评测，然后**又**加了一题 `#20`，此时去 `--rejudge`：

- 不加保护 → `data["detail"]["inject"]["20"]` **KeyError 崩溃**；
- 弱一点的保护 → 只判能查到的，**静默漏掉 #20**，而你误以为"19+1 题都重判过了"；
- **正确做法** → 跳过并**打印告警**："#20 无存档答案，需重跑 API"。

> 这又是"**检查器也会骗人**"的一个变种：一个不求甚解的脚本会让你以为覆盖全部，  
> 实际漏了题。**显式告警**才是负责任的写法。

### 4.4 改动四 · 命令行接入 `--rejudge`

#### 【原因】

函数写好了，但用户得能**从命令行调用**它，否则等于没有。

#### 【原理】`argparse` 的"可选值"参数

`argparse` 是 Python 自带的命令行解析库。难点在于：我们希望 `--rejudge` **三种用法都支持**：

1. 完全不写 → 走正常跑评测；
2. 只写 `--rejudge` → 用**默认**的报告 json；
3. 写 `--rejudge 别的.json` → 用**指定**文件。

这靠两个参数配合：

- `nargs="?"` = "**这个参数后面可以跟 0 个或 1 个值**"（`?` 就是"可有可无"）；
- `const=` = "**当你不给值时，用它**"（const = constant，常量）。

#### 【原代码】

```python
    ap.add_argument("--out", default=DEFAULT_OUT, help=f"报告路径（默认 {DEFAULT_OUT}）")
    args = ap.parse_args()
    ...
    modes = args.mode or sorted(STRATEGIES)
    run(cases, modes, args.out)          # ← 末尾直接就跑评测，没有别的分支
```


#### 【新代码】

```python
    ap.add_argument("--out", default=DEFAULT_OUT, help=f"报告路径（默认 {DEFAULT_OUT}）")
    default_json = os.path.splitext(DEFAULT_OUT)[0] + ".json"   # ② 算出默认 json 路径
    ap.add_argument("--rejudge", metavar="JSON", nargs="?", const=default_json,
                    help=f"从已有报告 json 离线重判，不调用 API"
                         f"（不带路径时默认 {default_json}）")
    args = ap.parse_args()
    ...
    if args.check:                       # ③ 优先：--check 只校验
        print("\n（--check 模式，未调用 API）")
        return

    if args.rejudge:                     # ④ 其次：--rejudge 走离线重判
        rejudge(args.rejudge, cases, args.out)
        return

    modes = args.mode or sorted(STRATEGIES)
    run(cases, modes, args.out)          # ⑤ 最后：什么都没传 → 正常跑评测（要花钱）
```

**关键点**：

| 行 | 写法                                           | 大白话                                                                                                                          |
| - | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| ② | `os.path.splitext(DEFAULT_OUT)[0] + ".json"` | `splitext` = "**把扩展名切掉**"：`…/eval_latest.md` → `["…/eval_latest", ".md"]`；取 `[0]` 得无扩展名字符串，再拼 `.json` → `…/eval_latest.json` |
| ② | `metavar="JSON"`                             | 只在 `--help` 里显示成 `--rejudge JSON`，纯装饰                                                                                        |
| ④ | `if args.rejudge:`                           | 没传时值是 `None` → 条件为假，跳过；传了就是路径字符串（非空）→ 为真                                                                                     |
| ④ | `return`                                     | **立即结束 `main()`**，不再往下走（否则会接着跑一遍花钱的评测）                                                                                       |
| ⑤ | 顺序                                           | **三个 `if` 的先后决定优先级**：`--check` 最先（零成本），`--rejudge` 其次（零成本），真跑最末（花钱）。零成本优先，是个好习惯                                              |

### 4.5 整体设计思想（面试可讲的一句话）

> **"调模型"是花钱的、慢的、有随机性的；"打分"是免费的、快的、确定性的。**  
> 把它们焊在一起，就会出现"改个判据要重烧一遍额度"这种荒唐事。  
> **`--rejudge` 的价值 = 把"改判据"从"必须重跑"降级为"零成本重判"。**

简历可写的一句：**"评测器支持离线重判，判据迭代不消耗模型额度。"**  
—— 这是**评测工程成熟度**的信号，比"我做了个 RAG"更能说明你懂工程。

## 六、措辞红线（不能说）

- ❌ 不能说"我实现了 RAG"——项目当前**没有检索层**，是全量注入。
- ❌ 不能说"完整评测体系"——对抗性测试/成本量化还没做。
- ❌ 引用任何数字必须带**模型名 + 日期 + temperature 口径**。
- ❌ 模型口径必须写**快照名**（`qwen-plus-2025-07-28`），不能写浮动别名 `qwen-plus`  
  —— 浮动别名会静默升级，导致同一份报告隔月不可复现。
- ❌ 旧"15 题 100%"作废，不许再对外引用。
- ❌ 不能说"我的系统经过了**完整/严格**的评测"——评测集（题与判据）**全部自出**，属**自证**。  
  （改说：「评测 19 题、**18 题计入分母**、94%（17/18），唯一失败是 `#4` 编造快递公司；
  但我知道这套题是我自己出的，所以我另外量化了它的自证风险」）
- ✅ 可以说："我**知道**我的评测是自证的，并且给出了**打破自证**的方法（引入外部语料）。"  
  —— 承认局限比掩饰局限更有说服力，这是本项目的真实亮点。

## 七、★ 战略重定位：第一性原理推导（2026-10-12）

> 起因：用户追问「现在最佳的优化方向，使这个项目更有含金量」。  
> 方法：暂时放下行业惯例，只从**基本事实 / 未验证假设 / 真实目标 / 资源约束**四层重新推导。

### 7.1 四个分层

**① 已确认、无法绕开的基本事实**

| #  | 事实                                         | 为什么绕不开                            |
| -- | ------------------------------------------ | --------------------------------- |
| F1 | 面试官**无法运行、无法复现、无法验证**你的系统（无环境/语料/Key）      | 他唯一能判断的是：**你讲得清吗、数字追溯得到吗、追问接得住吗** |
| F2 | 42 篇语料**全部由你撰写**（`data/docs/`）             | 知识库是**自建**的                       |
| F3 | 19 道题与全部 `pattern` **全部由你撰写**              | **考卷与考生同源**                       |
| F4 | 由 F2+F3 推出：**本项目是自闭环系统，它自产的所有数字都是自证的**     | 这是结构性弱点，不是操作失误                    |
| F5 | 模型会持续更换（用户明确表态）                            | 任何绑定具体模型的数字**都会过期**               |
| F6 | 秋招在即；你会 Python，不会 pytest / Docker / Web 后端 | 时间与能力都是硬约束                        |

**② 习惯性接受、却没验证过的假设**

| 假设                 | 为什么它不稳                                                    |
| ------------------ | --------------------------------------------------------- |
| 「功能越多越有含金量」        | 面试可讲的时长固定（~30 min）。功能越多，**单个功能能分到的讲解时间越少** → **加宽反而降低深度** |
| 「通过率高 = 系统好」       | 分母是你自己出的题，**而且分母口径本身就能改**——剔掉一道模型自带的常识题（`#7`），数字就从 95% 掉到 94%。它能证明的只有「在你的题、你的语料内答得对」 |
| 「不编造」是无条件优点        | 见 7.3 —— 它与「帮到顾客」这个产品目标**存在直接冲突**                         |
| 「语料是资产」            | 语料同时是**能力天花板**：语料没写的，系统永远答不出。**是资产也是负债**                  |
| 「全量注入 100% 证明系统可用」 | 分母自出；且 `#7` 这类「模型本来就知道的常识题」混在其中（其 `note` 已自认）             |
| 「多轮 3 题全过 = 多轮没问题」 | 3 题样本，且题也是自己出的                                            |
| 「上检索（BM25/向量库）是升级」 | 项目自己的数据说：44 篇下可能是**有损**的、把 100% 拉低                        |

**③ 真正想实现的目标**

不是「做一个客服系统」，而是：

> **获得一份能在面试中被追问 30 分钟而不崩的证据集。**

由此得到含金量的定义式：

```
含金量 = 可追溯性 × 判断深度 ÷ 功能数量
```

**④ 现实中的资源与约束**  
时间（秋招）、能力边界（无 Web / Git / Docker 工程底子）、无真实用户、无业务方、无预算、模型漂移。

### 7.2 原方案中，只在修补表面的部分

把已做与计划中的事项逐条对号：

| 事项                  | 性质            | 为什么只是表面                   |
| ------------------- | ------------- | ------------------------- |
| Step 0 事实底座对齐       | 管线卫生          | 消除文档与代码的矛盾，**不产生新认识**     |
| `--rejudge` 离线重判    | 工具            | 显著降低「改判据」成本，但**改的还是判据**   |
| 报告加「多轮题」列           | 测量精度          | 把测量切得更细，**被测对象没变**        |
| 模型口径统一 / fail-fast  | 管线卫生          | 正确且必要，但**零新信息**           |
| Step 2 token / TTFT | **仪表盘**       | 测的是**成本**，不是能力；且模型一变数字就作废 |
| ~~Step 4 语料扩容找失效点~~ | ~~**方向对，方法仍自证**~~ | ⛔ **2026-10-12 已挂起**：① 自己写语料、自己出题 → **还是自闭环**；② 需动 `data/docs/`，与语料封口冲突。改由 **A2 注入 A/B**（`source` 当 oracle）以 proxy 覆盖 |

**共同特征（这是本次推导的第一把刀）**：

> **全部在优化「测量精度」，没有一条在优化「被测对象」。**

它们是**必要条件（地基）**，不是**充分条件（建筑）**：让测量变得可信，但**被测对象从未被质疑过**。

### 7.3 从基本事实重新推导出的新路径

#### 推导链

1. 知识库 = 能力上限（F2）
2. 知识库是自己写的（F2）→ **上限自证**
3. 现有评测**全都在测「模型在给定知识库下答得对不对」**，从没测过「知识库本身够不够」
4. **`#4` 暴露了这个错位**：模型说出「顺丰 / 京东」被记为**模型违规**。但快递公司是**客观世界事实**，语料没写是**语料缺了一栏** → **把「知识库缺陷」记在了「模型」账上**
5. **`#7` 是同一件事的反面**：榴莲热量语料**写了**（`has`），通过。其 `note` 自认「普适知识题，A 策略也会通过」→ **用「模型本来就知道的常识」充当 `has` 题**
6. **把 4 与 5 并排看**：同一个「常识」——在 `#7` 被当作**通过的依据**，在 `#4` 被当作**违规的证据**。这不是模型的问题，是**知识库覆盖策略不一致**
7. **更深一层：`none` 这个分类本身是坏的**

   `none` 的定义是「语料里没有」。但「语料里没有」**不等于**「正确行为是拒答」：
   | 题            | 语料有吗 | 答案客观可得吗         | **当前**正确行为（两者一致） | 长期处置（**区别在这里**）        |
   | ------------ | ---- | --------------- | ----------------- | ---------------------- |
   | `#4` 你们发什么快递 | ❌    | ✅ 客观存在（世界知识里就有） | 不编造、说明信源里没有       | **补语料** → 补完后升级为 A 类，应当答得出 |
   | `#9` 物流到哪了   | ❌    | ❌ 客观不可得（需实时接口）  | 不编造 + 拒答 + 指路      | **保持拒答** → 静态语料永远补不上这一栏 |

   **⚠️ 2026-10-12 更正（本人拍板）**：这两题的**当前正确行为其实是一致的**
   （都不编造）。我上一版写的「两者的正确答案是相反的」**表述有误**，已作废。
   真正的分界不是「答案相不相反」，而是 **「这个洞能不能靠补语料填上」**：
   - 能填 → **B·知识盲区（`gap`）** → 去改 `data/docs/*.md`
   - 填不上 → **C·能力边界（`boundary`）** → 去改提示词里的指路话术

   → 用「正确答案」当分类标准，会把这两题错当成同一件事（因为当前行为确实一样）；
   改用 **「失败时该修哪个文件」** 当标准，两者立刻分开。**这正是 `kind` 的设计原点。**

#### 新路径（一句话）

> **把优化对象从「模型的行为」上移到「知识库的边界」——**  
> **因为知识库才是一切行为的天花板，而它从未被审计过。**

#### 三步（顺序不能换）

| 步  | 内容                                                          | 为什么是这个顺序           |
| -- | ----------------------------------------------------------- | ------------------ |
| N1 | **按「正确答案是什么」重划题型**（而非按「语料有没有」）                              | 零成本、立刻可做；先修正地图，再走路 |
| N2 | **引入外部语料**（真实公开的电商配送/售后条款）替换或补充部分自建语料，在同一批题上看表现             | **这是唯一能打破自证的动作**   |
| N3 | **覆盖度审计**：标出「语料有 / 语料无但客观可查 / 语料无且不可确定」，据此决定「补语料」还是「改提示词指路」 | 让每个失败都有**明确的下游动作** |

#### 题型重划（N1 的具体形态）

&#x6309;**「失败时该修什么」**&#x6765;分类 —— 这才是分类的本质需求：

| 新类型    | 定义          | 失败时该修     | 现有题                            |
| ------ | ----------- | --------- | ------------------------------ |
| A·事实覆盖 | 答案在语料内      | 修模型/提示词   | `#1,2,3,6,10,11,12,13,14,19`（`#7` 已移出分母，见下） |
| B·知识盲区 | 语料无，但答案客观存在 | **补语料**   | `#4`                           |
| C·能力边界 | 答案客观不可得     | 保持拒答 + 指路 | `#9`                           |
| D·约束红线 | 行为规范        | 修提示词      | `#5,8,15,17`                   |

> 现在 `B` 与 `C` 都被塞在 `none` 里。**拆开它们，每个失败才知道该往哪修。**

**第四根轴：`counted`（这题算不算进分母）** —— 与 A/B/C/D **正交**，不是一个新类型。
`#7`（榴莲热量）属于 A 类，但**模型自带这个常识、一句语料不给也能答对**，
把它计入分母等于「拿模型本来就有的本事给你的优化记功」。
→ 标记 `counted: false`，排除在通过率外、单独列为**对照组**（但仍保留在题库里当校准项）。
→ 详见 7.7 节。

#### 由此产生的第一句面试金句

> **「我发现我把『知识库缺陷』记成了『模型违规』。**  
> **快递公司是客观事实，我的语料漏了它——该修的是语料，不是判据。」**

这句话的价值：它证明你能**区分「系统缺陷」与「模型缺陷」**——这正是 AI 应用岗最核心的判断力。

### 7.4 这条路径成立的前提

| #  | 前提                            | 可行性 | 风险                       |
| -- | ----------------------------- | --- | ------------------------ |
| P1 | 能找到可信的**外部语料**（真实电商公开条款、配送说明） | 高   | 需辨别真伪，不能随便抄              |
| P2 | 题型重标必须**你本人**做                | 中   | AI 代劳 → **又变成自证**，整条路径失效 |
| P3 | 有时间做「替换外部语料后的对比实验」            | 中   | 取决于秋招节奏                  |

> ⚠️ **P2 是整条路径的命门**：这条路径的全部价值，都建立在「标注由人做」之上。  
> 一旦用 AI 来标，自闭环只是从"人自证"变成"AI 自证"，问题一模一样。

### 7.5 验证它的第一步（零成本）

**不改代码、不调 API、不扩语料。只做一件事：**

> **用 7.3 的 A/B/C/D 四分类，把现有 19 题重标一遍。**  
> 只改 `note`（必要时 `category`），**`pattern` 与代码一律不动**。

观察三个点：

1. 哪几题的归类会**翻转**？（预计 `#4` 从「不许答」→「应声明边界」）
2. 哪些题会被暴露&#x4E3A;**「常识充数」**？（`#7` 已有意识，但仍是 `has`、仍计入事实题通过率）
3. 有没有题**无法归类**？—— 无法归类的题，往往才是设计缺陷最集中的地方

**为什么这是第一步而不是「先扩语料」**：

- 零成本，今天就能做；
- 它本身即产出面试素材（"我用第一性原理检查了自己的分类，发现…"）；
- 它**不依赖 API 额度、不依赖外部语料**，风险最低。

| 产物 | 说明 |

| `eval/cases.jsonl` | 每题新增 `kind` 字段（`fact`/`gap`/`boundary`/`rule`） |

**加一根正交的轴，就能把旧的分类混用当场暴露出来。**

### 7.7 ★ 四题核验结论（用户拍板，2026-10-12）

7.5 要求"分类必须本人做"。以下是**用户本人**对 4 道争议题的最终裁定：

| 题 | 我的草稿 | **用户裁定** | 落地动作 |
| --- | --- | --- | --- |
| `#4` 发什么快递 | `gap` | **认同**：快递公司是客观事实，语料漏了这一栏，**该补语料** | 保留 `gap`，进"待补语料"清单 |
| `#7` 榴莲热量 | `fact` | **不应继续留在事实题分母** | 新增 `counted:false`，移出分母、单列对照组 |
| `#9` 物流到哪了 | `boundary` | **不是"相反答案"**（推翻我的表述） | 修正 7.3 与 README 的措辞 |
| `#15` 帮登记 | `rule` | **不要改成 `constraint`** | 归档为 `KNOWN_EXCEPTIONS` 已备案例外 |

#### （1）由 `#7` 引出的**第四根轴**：`counted`

原设计只有一根轴（`kind` = 失败时该修什么）。`#7` 的裁定暴露了**第二根轴**：

> **「这道题的通过，能不能归功于知识库接入？」**

`#7` 属于 `fact`（语料里确实写了），但**模型不靠语料也能答对**——
它在分母里每通过一次，都在**给知识库记一笔不属于它的功**。

落地：新增 `counted` 字段（默认 `true`，不写即计入），`#7` 标 `counted: false`；
`rate()` 过滤条件加 `c.get("counted", True)`；报告头部写明分母、并单列「对照组题」。

**⚠️ 由此产生第三次数值口径变化：**

| 口径版本 | 分母 | 结果 | 变化原因 |
| --- | --- | --- | --- |
| 09-30 旧报告 | 10 题 | B 100% / A 30% | **已作废**（题数 / temperature / 报告结构三变） |
| 10-10 首跑 | 19 题 | 84% | 首次多轮 + 首次 `temperature=0` |
| 10-10 重判 | 19 题 | 95% | 修 `#12`/`#15` 判据 |
| **10-12 重判** | **18 题** | **94%** | **剔除对照组 `#7`**；`#4` 仍是唯一真失败（17/18） |

> 数字从 95% 变 94%，**不是系统变差**，是**分母口径变干净了**。
> 引用时必须带分母：**「18 题计入分母、17 通过、唯一失败 `#4`」**。

#### （2）由 `#9` 引出的**表述更正**

我上一版写「`#4` 与 `#9` 的正确答案是相反的」——**这是错的**，已改。
两者**当前正确行为一致**（都不编造），区别只在**长期处置**
（`#4` 能靠补语料修、`#9` 永远不能）。详见 7.3 更正段。

#### （3）由 `#15` 引出的原则：**校验器必须有"已备案"通道**

`#15` 的非常规搭配是**有意为之**。若校验器每次都对它报警，你会开始**无视报警**
——而**一个被无视的校验器等于没有校验器**。
所以 `check_kinds.py` 把输出分三档：`❌ 错误` / `📌 已备案例外` / `⚠️ 待判断提示`。

### 7.8 N3 落地：知识库覆盖度审计（2026-10-12）

> 起因：用户反馈「感觉好像一直在补语料和修改」——要求**一次性做完**，不要一条一条挤牙膏。
> 判断：**这条抱怨是对的**。补语料的正解不是改一条，而是把整个知识库的空白**一次扫清**。

#### 工具：`tools/audit_coverage.py`（零成本，不调 API）

| 段 | 检查什么 | 能抓出什么 |
| --- | --- | --- |
| A 断链检测 | 文档写了《某某文档》，文件是否存在 | 交叉引用指向不存在的文件 |
| B 分类覆盖 | 每类文档的篇数与字数 | 结构偏科（百科 20 篇 vs 客服 1 篇） |
| C 栏目一致性 | 同前缀文档的二级标题是否统一 | 模板漂移（20 篇百科是否都 5 栏） |
| D 问题域扫描 | 预置 18 个「生鲜电商客服问题域」词表，零命中 = 候选盲区 | **真正的知识盲区** |

#### ★ 本轮最重要的发现：审计工具自己也会骗人

D 段第一次跑出来，`快递承运商` 显示 **✅ 命中**（命中词 `中通`），差点据此推翻 `#4` 的结论。
核查上下文后：

```
「中通」@服务-客服渠道与工作时间.md：…您可以在 App 或小程序中通过「我的 → 联系客服」进入…
                                    ^^^^ 假阳性来自「小程序中通过」
```

**这是本项目第 6 次踩「字符串存在 ≠ 语义命中」——而且这次踩的是我自己刚写的工具。**
修法：**命中一律打印 ±12 字上下文**，让人工核对语义角色，而不是只报「命中 N 处」。

一次抓出 4 个同类假阳性：

| 表观命中 | 真实来源 | 结论 |
| --- | --- | --- |
| `中通` | 小程序**中通**过… | 承运商真缺失 |
| `有机` | 有**机**酸 | 有机认证真缺失 |
| `最低消费` | 优惠券**最低消费**门槛 | 起送价语义不符 |
| `发货时间` | 以商品页**预售**说明为准 | 通用发货时效真缺失 |

#### ★ 方法论产出：「缺失」分三种，不能一律补

见到洞就填，会把**设计**当成**缺陷**：

| 缺失类型 | 例子 | 处置 | 补错的后果 |
| --- | --- | --- | --- |
| ① 该补的缺 | 快递承运商（客观事实、业务必有、答案稳定） | **补语料** → 归 `gap` | 不补则一直误记为"模型编造" |
| ② **必须保持**的缺 | 实时物流轨迹、售后工单进度 | **保持拒答 + 指路** → 归 `boundary` | **补了 = 教会模型虚假承诺**，直接反噬 `#9`/`#15` |

### 2026-10-12 · 模型口径治理（应对"模型选用会一直变化"）

- **触发**：用户明确"我的模型选用会一直变化"。勘察发现模型名散落 **3 处且互不一致**：

  漏配 `.env` 时它会**悄悄**用另一个模型跑，而报告头部仍写着真实模型名  
  → **"指标管道会骗人"的又一变种**（你以为是 A，跑的是 B，数字全废）。
- **改法（3 处）**：
  1. `app.py:278` → `model = os.environ.get('LLM_MODEL')`；缺失则 `st.error(...)` + `st.stop()`
  2. `tools/eval_run.py:336` → 同上；缺失则 `raise SystemExit(...)`（fail-fast）
  3. `.env.example` → 注释标明**必填**、**用快照名不用浮动别名**
- **确立原则**：**模型身份的唯一来源 = `.env` 的 `LLM_MODEL`；代码不写死兜底。**
- **配套**：必须用**带日期的快照名**（`qwen-plus-2025-07-28`）而非浮动别名（`qwen-plus`），  
  否则同一份报告隔月不可复现。
- **验证**：`ruff` 无语法错、无未定义名（11 条均为风格建议）；`--check` 19 题通过。
